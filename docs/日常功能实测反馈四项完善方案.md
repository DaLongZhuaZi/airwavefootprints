> 版本：2026-10-27，基于用户对最新版的实测反馈。
> 基线：main 尖 `b9c1d8e`（已合入：安防扫描、Wi-Fi 体检、场景包、评分引导、反跟随提醒、卡片升级、图鉴、新面孔；版本 1.1.0 / 1010001）。
> 与《日常用户拓展落地文档-审计修订版.md》的关系：本文档是它的后续篇，不是替代。落地文档的 P0–P2 安全部分已合入 main；找东西体系、看板、找车、日常首页仍在找东西专题里，**不属于本文档**。
> 证据说明：四项反馈来自用户对 feat 版（`0947b94`）的实测；其中安防、体检、图鉴、新面孔四页已原样合入 main，诊断直接适用；找东西与日常首页部分已按 main 现状（`da11a71` 体系）重写，实施时**不得引入 feat 的 OwnDeviceProfile / FindModel / OwnDeviceCenter / DailyPage / DeviceBoardPage 体系**。

## 总原则

- **简单 = 首屏只给结论和关键数字，但每个数字都能点进详情**。不做“只有标题和一句描述”的卡片，也不做“只说大概”的汇总页。
- **不承诺做不到的事**。扫描结论只分“确认 / 可疑 / 未发现”，绝不说“安全”“已排除”。
- **分期可独立发版**：第一期先修可用性（命名、安防被动层、图鉴性能与联动），第二期再做内容充实与玩法。

## 分期

- **第一期（P3-1）**：第 2 项命名回退链、第 3 项安防被动层与可疑清单、第 4 项图鉴性能与联动。
- **第二期（P3-2）**：第 1 项页面内容充实（详情入口 / 历史 / 趋势 / 空状态动作）、第 4 项图鉴玩法（等级勋章）、第 3 项人工排查清单。

## 第 1 项：日常功能页面内容空洞

### 现象与根因

日常首页三张大卡只有标题加一句描述，没有任何实时数据；安防页扫完只给总数、分类 Top、新面孔数、跟随分，**没有可疑设备清单，点不进去看是哪台、没历史扫描记录、没下一步该做什么**；看板卡只到名字 / 在附近 / 电量为止，没有信号趋势和直达动作。每页都停在汇总层，详情入口没接。

### 修复清单（仅针对 main 已有页面；日常首页与看板随找东西专题）

- **安防页**：汇总之下补三块——可疑设备清单（每台点进详情：证据分项、厂商、首次出现、信号轨迹）、人工排查清单（见第 3 项）、历史扫描记录（时间、总数、可疑数，点进可看当次结果）。
- **Wi-Fi 体检页**：在现有信道建议与房间分档之外补当前 AP 详情（SSID、BSSID、频段、信道、拥挤度）与历史趋势（同一房间历次分档变化）；“一键优化”后要有跟进项（改信道后复测提醒），不能建议完就没下文。
- **图鉴页**：详情入口见第 4 项联动；另补分类进度（每类点亮几 / 共几），不要只有一个总数。
- **新面孔页**：每条新面孔点进设备详情（证据、首次出现、信号轨迹、手动“这是我家的”移出基线入口），不要只列名字。
- **通用**：空状态不能只有一句话，要给动作按钮（去认领 / 去扫描 / 去开蓝牙）；每个汇总数字都要可点进对应清单或详情。

### 验收

- 安防、体检、图鉴、新面孔四页，从汇总数字出发都能在 ≤2 次点击内到达单台设备详情；空状态均有下一步动作按钮；历史记录与当前数据对账一致。

## 第 2 项：找东西“未命名设备”（以 main 的 `da11a71` 体系为准）

### 现象与根因（main 现状已核实）

- main 的 `FindPage.titleOf` 与 `FindClaim` 的标题逻辑都是“名空 → 显示『未命名设备』”，**只有一级回退**。
- 名称来源只有两条，且两条都经常为空：① BLE 广播名——很多设备广播里根本不带名字，要名字得连 GATT 读设备名（0x2A00），那是主动连接，违背“只接收不连接”底线，不能做；② 系统配对名——`getRemoteDeviceName` 对纯 BLE 配对经常不响应；main 的配对模块虽已覆盖 BLE 与星闪双通道（`getRemoteDeviceName` 两参调用 + `NearLink.getDeviceName`），但**扫描结果没有用配对名去 enrich**：Sighting 建出来时用的就是扫描到的 `displayName`，空了就是空。
- 扫描 deviceId 与配对虚拟地址未必同值（落地文档附录 A 的 V1 验证项），地址对不上时去重与补名都会失效；随机 MAC 还会让地址一变就断档，无名条目越积越多。
- 手头有弱身份可用，全都没接进命名：CoD 类别（耳机 / 音箱 / 手表…）、BLE 厂商 companyId（解码已出，radiodb 有 IEEE CID 厂商表）、特征库命中的 fleet 名、WiFi SSID。

### 修复清单

- **命名回退链**（落到 main 的展示层：`FindPage.titleOf` 与 `FindClaim` 的标题装配，新增一个纯逻辑命名函数 + 单测）：自定义 / 认领名 → 配对名（BLE + 星闪双通道查）→ 广播名 / SSID → 特征库 fleet 名 → CoD 通用名（蓝牙耳机 / 智能手表…）→ 厂商名 + 类别（如“华为 · 蓝牙耳机”，companyId 查 CID 厂商表）→ 兜底“未命名设备 · 尾号 XXXX”（地址后 4 位，区分多台无名设备）。
- **扫描 enrich**：装配 Sighting 候选时，`displayName` 为空则用配对名补（按地址查，查不到走指纹匹配）；并补做 V1 验证（扫描 deviceId 与配对虚拟地址是否同值），不同值时走指纹匹配关联，不得假装地址直配成立。
- **列表改名入口**：候选行长按 / 认领时可直接改名，改名后所有页面统一；无名条目旁用一句话说明原因（“该设备广播里没有名字”），别让用户以为是 bug。
- **边界**：GATT 读名需要连接，不做；改善后无名率会大降，但不可能归零，验收不以“零无名”为标准。

### 验收

- 常用自有设备组（耳机 / 手表 / 音箱 / 车机 / 防丢器）真机实测：回退链逐级可测（单测覆盖每一级）；配对名补全后，已配对设备的无名率明显下降；同名 / 无名多台时尾号可区分；V1 验证结论写入代码注释（同值 / 不同值 + 分支）。

## 第 3 项：安防扫描要真正体现“安防”（酒店 / 租房场景）

### 现象与根因

当前 `SecurityScan` 只产出总数、分类 Top、新面孔、跟随分，没有任何“可疑设备”判定；611 条特征库是通用设备特征，没有摄像头 / 窃听器专项；旧口径还禁止提“防偷拍”，页面只能说“身边比较安静”。用户要的能力现在确实没有。

### 修复清单

#### 3.1 被动层（不改底线，第一期做）

- **特征库新增“疑似摄像头”类别与规则**（复用现有 catalog 结构：fleet + rules，radio 覆盖 WIFI / BLE；每条规则带证据等级与来源注释，可单测）：
  - 厂商 OUI 前缀：60+ 摄像头厂商（海康、大华、Axis、Reolink、Wyze、Ring、Nest、TP-Link、Ubiquiti、Amcrest、Lorex、Foscam、小米 / 萤石、Wansview、汉邦等）及偷拍常用芯片方案商（乐鑫 Espressif、海思 HiSilicon、雄迈 Xiongmai、涂鸦 Tuya）。OUI 前缀以 IEEE 公开注册表为准，厂商名以 radiodb 的 CID 表为准。
  - SSID / 主机名模式：IPCAM、IP_Camera、Camera_XX，及含 cam / ipc / nvr / dvr 的主机名。
  - BLE 名模式：含 camera / cam / IPC 的广播名，及已知摄像头厂商的 manufacturer companyId。
  - mDNS / SSDP 服务特征：宣告视频能力的服务（`_http._tcp` 含摄像头型号、ONVIF 相关服务）。
- **可疑设备清单**：安防页输出按证据分级的清单（确认 / 可疑两档，见 3.3），每台点进详情看证据分项（命中了哪几条规则、厂商、首次出现、信号轨迹、建议动作：肉眼复核该位置）。
- **与跟随评分的关系**：可疑清单与跟随评分是两条线，不要互相折算；一台设备可以同时出现在两边。

#### 3.2 局域网探测层（待用户拍板，本期不做）

仅在用户主动触发安防扫描、且手机已连当前 WiFi 时，对内网做：ARP 扫网段 → OUI 查厂商 → 探端口（附录 A 的端口表）→ mDNS / SSDP 监听 → 置信度打分。这是检出联网摄像头的关键，没有它只能检出广播名带特征的极少数。**但它属于主动探测，会放宽“只接收不连接”的底线，必须用户明确批准后才启动**；未批准前，安防页要写清“当前只做被动扫描，局域网探测未开启”。

#### 3.3 结论分级与能力边界（文案口径）

- 结论只分三档：**确认**（多信号印证，如厂商 OUI + 视频服务端口双命中）、**可疑**（单强信号，如已知摄像头厂商 OUI 或视频端口单命中）、**未发现**（本次扫描无命中）。绝不说“安全”“已排除”。
- 必须在结果页写清能力边界：不联网 / 纯本地存储摄像头、关机摄像头、酒店 WiFi 客户端隔离、GSM 窃听器（走蜂窝网络，WiFi / BLE 根本扫不到）都无法用扫描发现。
- **人工排查清单**（第二期）：关灯手电找镜头反光、查烟感 / 插座 / 镜子 / 空调出风口、断电后仍发热的设备、夜视红外灯；清单按房间逐项打勾，扫不出来的部分由它补。

#### 3.4 窃听器覆盖说明（诚实口径，写进帮助页）

- WiFi / BLE 类拾音设备（带音频服务 / 特定厂商）可进特征库，按 3.1 同一套规则处理。
- GSM / SIM 类窃听器需要射频硬件，应用内只能给排查项，**不得宣称能检出**。

### 验收

- 被动层规则全部有单测；构造场景真机验证：已知摄像头厂商 OUI 设备、含 IPC 的 SSID、视频服务宣告三类各至少一例命中对应档位；结果页能力边界文案齐全；未批准前局域网探测代码不得合入（grep 验收：无 ARP 扫网段 / 端口探针调用）。

## 第 4 项：图鉴卡顿、联动断、不好看、没玩法

### 现象与根因（main 已合入的 Dex / DexPage 实测代码）

- **卡**：进页就全量读 2000 条历史再全量重算；`buildDex` 里每条 fleet 的稀有度都要扫一遍全库（611×611 ≈ 37 万次比较）；Grid 用 `ForEach` 而非 `LazyForEach`，611 个格子一次性全建出来。
- **联动断在三处**：点亮依赖历史记录里的 signatureId，特征库更新后旧 id 可能失效，旧点亮对不上新库；图鉴只在进页时重算，特征库在线更新后不刷新；详情页注释说接 `DeviceExplain` 文案，实际只显示了类别、稀有度、次数，没有解释文案，也没有“在特征库里看它”“去实时页找它”的跳转。
- **不好看、没玩法**：全部格子同一个电波图标，只靠颜色区分稀有度；`DexSummary` 只有总数 / 已见 / 今日新增，没有等级、勋章、成就系统。

### 修复清单

- **性能（第一期）**：稀有度按类别预计算一次（Map 缓存，不再每条扫全库）；点亮统计增量缓存，只在历史或特征库变化时重算；Grid 改 `LazyForEach` + 分页（已点亮在前分页加载）；进页先显缓存再后台刷新。
- **联动（第一期）**：特征库更新后做 id 映射（旧 signatureId 按 fleet 名归一）并订阅 catalog 更新事件自动刷新；详情页接通 `DeviceExplain` 文案，加“特征库详情”和“去实时页找它”两个跳转；点亮统计与历史数据对账一致（与落地文档 P2-11 验收口径相同）。
- **视觉与玩法（第二期）**：每类专属图标与配色，已点亮用设备类图标、未点亮剪影；等级（按点亮数与稀有分升级，如观察者 → 探索者 → 猎手 → 大师）；勋章（首台星闪、首台监控类、集齐一类、连续 7 天新发现）；分类进度条；首次点亮弹层 + 分享卡。稀有度口径不变（库内同类数量，可对账），文案注明是“库内稀有度”。

### 验收

- 图鉴页首屏不再卡顿（真机实测：进页到可交互无可见掉帧堆积；2000 条历史下重算不再全量 O(n²)）；特征库更新后图鉴自动刷新且旧点亮不丢；详情页两处跳转可用；等级 / 勋章 / 分类进度 / 首次点亮弹层真机通过。

- **未发现**：本次扫描无命中——不等于安全，须与人工排查清单配合看。
