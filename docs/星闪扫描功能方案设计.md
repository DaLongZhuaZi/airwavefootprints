# 星闪（NearLink）扫描功能方案设计

> 依据：华为开发者文档 `@ohos.nearlink.*`（API 26.0.0+），以及本机 SDK 的
> `PermissionDefinitions.json`。所有权限等级均为实测查证，非推测。

## 一、结论摘要

1. **技术上可行**，且能复用现有 BLE 扫描器架构，UI 层几乎无需改动。
2. **全程不涉及任何 ACL 受限权限** —— 星闪全部能力只需要一条用户权限
   `ohos.permission.ACCESS_NEARLINK`（`user_grant / normal / NORMAL`）。
3. **需要新增第 4 条隐私权限**（即上述 ACCESS_NEARLINK），接入现有「先说明再申请」流程。
4. **有硬件门槛**：错误码 `801` 表示芯片不支持，必须在运行时探测并按能力降级。
5. **唯一实质缺失**：三条 MAC 权限是 ACL=SYSTEM，拿不到真实 MAC，
   因此无法做跨会话的稳定设备身份追踪。
6. **连接类与测距能力权限上完全可用**，不纳入是「只接收不连接」的**产品选择**，
   不是权限限制 —— 这个区分必须写清楚。

---

## 二、权限分析（实测查证）

### ✅ 本方案不涉及任何 ACL 受限权限

星闪**全部能力只需要一条用户权限**：`ohos.permission.ACCESS_NEARLINK`。
经实测查证（本机 SDK `PermissionDefinitions.json` + 华为官方文档逐模块核对）：

| 模块 | 需要权限 | 是否 ACL |
|---|---|---|
| `nearlink.scan` | `ACCESS_NEARLINK` | **否** |
| `nearlink.manager` | `ACCESS_NEARLINK`（部分接口无需权限） | **否** |
| `nearlink.advertising` | `ACCESS_NEARLINK` | **否** |
| `nearlink.ssap` | `ACCESS_NEARLINK` | **否** |
| `nearlink.dataTransfer` | `ACCESS_NEARLINK` | **否** |
| `nearlink.cdsm` | `ACCESS_NEARLINK` | **否** |
| `fusionConnectivity.ranging` | **无需权限** | **否** |

**`ohos.permission.ACCESS_NEARLINK` 本身是 `user_grant / normal / NORMAL`**，
普通应用可直接申请，**不需要向应用市场单独申请 ACL**。

### ❌ 仅有的三条 ACL 权限，本方案完全不需要

| 权限 | grantMode | level | ACL | 用途 |
|---|---|---|---|---|
| `ohos.permission.MANAGE_NEARLINK` | system_grant | system_basic | **SYSTEM** | 程序化开关星闪、管理配对 |
| `ohos.permission.GET_NEARLINK_LOCAL_MAC` | system_grant | system_basic | **SYSTEM** | 读取本机真实 MAC |
| `ohos.permission.GET_NEARLINK_PEER_MAC` | system_grant | system_basic | **SYSTEM** | 读取对端真实 MAC |

这三条**不声明、不申请、不使用**。它们带来的限制见第三节。

### ⚠️ 关键更正：星闪没有独立的系统设置项

**系统设置里本应用只有一项「设备发现和连接」，它同时管理蓝牙与星闪。**

因此：
- 应用内**只显示「设备发现和连接」一项**，不出现单独的「星闪」条目；
- `ACCESS_NEARLINK` 作为**该条目覆盖的第二条底层权限**存在，
  申请时与蓝牙一起逐条补齐（见 `FieldwatchPermissionSpec.permissionIds`）；
- 隐私协议中星闪并入第一节，不单列。

### 权限方案

- 在 `module.json5` 声明 `ohos.permission.ACCESS_NEARLINK`，带 `reason` 与 `usedScene`，
  与现有 3 条用户权限走**同一套「先说明再申请」流程**。
- 接入 `FieldwatchPermissions` 目录，名称与系统设置里显示的一致。
- **写入隐私协议**：这是第 4 条需要用户主动授权的权限。
- **运行时门控**：`manager.isNearLinkSupported()` 返回 false 时，**不申请该权限**、
  不显示任何星闪入口 —— 不能在无此硬件的设备上向用户索要一个用不到的权限。

### 地址语义的不确定性（需实测）

`ScanResults.address` 会返回一个地址，但 `GET_NEARLINK_PEER_MAC` 属于系统级权限。
因此该地址**很可能不是真实 MAC，而是可解析的匿名地址**。
**设计上必须把它当作「可能变化的标识」**，不能当作稳定设备 ID：
- 设备去重与关注目标匹配应以 `deviceName + deviceClass` 为主键候选，
  地址仅作为辅助；
- 界面上不要把它标成「MAC 地址」。
**这一条需要真机实测确认**，不能凭文档推断。

## 三、在「不涉及 ACL」前提下，最终成品能实现哪些功能

### 3.1 能做（全部只需 `ACCESS_NEARLINK` 一条用户权限）

| # | 功能 | 依据 | 与 BLE 对等性 |
|---|---|---|---|
| 1 | **星闪被动扫描** —— 发现周围星闪设备 | `scan.startScan` / `onDeviceFound` | 完全对等 |
| 2 | **设备名称显示** | `ScanResults.deviceName` | 完全对等 |
| 3 | **信号强度定位** —— RSSI 决定雷达半径 | `ScanResults.rssi`（**须过滤 127 无效值**） | 完全对等 |
| 4 | **设备类型识别与图标** | `ScanResults.deviceClass` | 完全对等（BLE 靠特征库，星闪靠官方枚举） |
| 5 | **广播数据解析** —— 送入特征库匹配 | `ScanResults.data`（ArrayBuffer） | 完全对等 |
| 6 | **可连接性标注** | `ScanResults.isConnectable` | 比 BLE 更明确 |
| 7 | **本机星闪名称** | `manager.getLocalName()` | BLE 无对应，独有 |
| 8 | **能力探测与开关状态** | `isNearLinkSupported()` / `getState()` | 更完善（BLE 只有开关状态） |
| 9 | **雷达 / 列表 / 筛选 / 详情 / 标签 / 关注 / 聚类** | 复用同一份 `sightings` | **完全对等，上层零改动** |
| 10 | **扫描结果过滤** | `ScanFilters`（address / deviceName） | 比 BLE 更省电（官方建议用过滤） |

### 3.2 做不到（受三条 ACL 权限限制）

| # | 做不到的事 | 原因 | 影响 |
|---|---|---|---|
| 1 | **拿到真实 MAC 地址** | `GET_NEARLINK_PEER_MAC` / `LOCAL_MAC` 是 ACL=SYSTEM | `ScanResults.address` **很可能是匿名/可解析地址**，会随时间变化 |
| 2 | **跨会话的稳定设备身份** | 同上 | 无法可靠实现「这台设备上周也出现过」这类历史追踪 |
| 3 | **程序化开关星闪 / 管理配对** | `MANAGE_NEARLINK` 是 ACL=SYSTEM | 只能在界面上提示用户去系统设置开启 |

**应对设计**：
- 设备去重与关注目标匹配**以 `deviceName + deviceClass` 为主键候选**，地址仅作辅助；
- 界面上**不把该地址标注为「MAC 地址」**，避免误导；
- 详情页对地址加一行说明：星闪地址可能随隐私策略变化。

### 3.3 权限允许、但我们**主动选择不做**（产品原则，不是权限限制）

> **重要区分**：以下能力**只需要同一条 `ACCESS_NEARLINK`，没有任何 ACL 障碍**。
> 不做它们是本应用「只接收、不连接」原则的选择，不是做不到。

| 能力 | 需要的权限 | 为什么不做 |
|---|---|---|
| `nearlink.advertising`（对外广播自己） | `ACCESS_NEARLINK` | 本应用不对外广播 |
| `nearlink.ssap`（服务发现与连接） | `ACCESS_NEARLINK` | 违反「不连接」原则 |
| `nearlink.dataTransfer`（数据传输） | `ACCESS_NEARLINK` | 同上 |
| `nearlink.cdsm`（连接与数据管理） | `ACCESS_NEARLINK` | 同上 |
| `fusionConnectivity.ranging`（星闪测距） | **无需权限** | 需建立会话，与被动监听冲突；建议放到「单信号跟踪模式」 |

**星闪测距值得特别说明**：它**不需要任何权限**，且能给出**真实距离**而非 RSSI 估算，
是本应用真正的差异化点。它唯一的代价是**需要双方建立会话**，
因此不适合混进被动雷达，而应作为需要用户明确知晓的独立模式。

### 3.4 一句话总结成品能力

> **在完全不涉及 ACL 权限的前提下，星闪可以做到与蓝牙「完全对等的被动观测体验」**：
> 发现、识别、定位、分类、筛选、记录、关注、聚类——一样不缺，
> 而且比蓝牙多了「官方设备类型枚举」和「本机名称查询」两项能力。
>
> **唯一的实质缺失是「稳定的设备真实身份」**：拿不到真实 MAC，
> 因此无法做跨会话的历史身份追踪。这是 ACL 限制的直接后果，
> 需要在产品说明中如实告知用户。

## 四、API 能力盘点与取舍

| 模块 | 能力 | 是否纳入 | 理由 |
|---|---|---|---|
| `nearlink.scan` | 发起/停止扫描、订阅结果 | **纳入** | 被动监听，与 BLE 扫描同性质 |
| `nearlink.manager` | 能力探测、开关状态、本机信息 | **纳入** | 用于能力门控与状态提示 |
| `nearlink.constant` | `DeviceClass` 等枚举 | **纳入** | 映射设备类型图标 |
| `nearlink.advertising` | 对外广播自己 | **不纳入** | 本应用不广播 |
| `nearlink.ssap` | 服务发现/连接 | **不纳入** | 违反「只接收不连接」原则 |
| `nearlink.dataTransfer` | 数据传输 | **不纳入** | 同上 |
| `nearlink.cdsm` | 连接与数据管理 | **不纳入** | 同上 |
| `fusionConnectivity.ranging` | 星闪测距 | **待定，见第六节** | 可能给出真实距离，但需建立会话 |

## 五、架构设计

### 5.1 复用现有扫描器契约（零改动接入）

现有 `IFieldwatchRadioScanner` 已经是抽象接口，`FieldwatchBleScanner` 与 Wi-Fi 扫描器都实现了它。
新增 `FieldwatchNearLinkScanner implements IFieldwatchRadioScanner` 即可接入现有协调器，
**状态机、重试、错误上报、UI 层全部复用**。

```
IFieldwatchRadioScanner
  ├── FieldwatchBleScanner        (现有)
  ├── FieldwatchWifiScanner       (现有)
  └── FieldwatchNearLinkScanner   (新增)
```

导入方式与 BLE 完全一致：`import { scan, manager } from '@kit.ConnectivityKit';`
（BLE 用的是同一个 kit，无需引入新依赖。）

### 5.2 数据映射

| `ScanResults` | `ScanObservation` | 处理要点 |
|---|---|---|
| `address` | `address` | 视为可能变化的匿名标识 |
| `deviceName` | `name` | 长度 [0,30]，空串时回退到地址 |
| `rssi` | `rssi` | **127 表示无效**，必须过滤，否则会在雷达上出现虚假的强信号 |
| `deviceClass` | 映射为 `SignatureClass` | 用于选设备类型图标，实现与 BLE 一致的观感 |
| `data` (ArrayBuffer) | 原始字节 | 交给现有特征库引擎匹配 |
| `isConnectable` | 记录为事实字段 | 详情页展示 |

### 5.3 枚举与类型扩展

- `RadioKind` 增加 `NEARLINK`。
- 调色板为星闪分配一个**独立颜色**（与 BLE 绿 / Wi-Fi 青区分开）。
- `FieldwatchDeviceTypeIcon` 增加 `deviceClass → 系统符号` 映射，复用现有 `deviceClassSymbol` 思路。

## 六、用户体验：与蓝牙保持一致

要做到「尽可能与蓝牙一样」，需要对齐以下每一处：

| 场景 | 处理 |
|---|---|
| 实时雷达 | 星闪设备以同规格图标出现在圆环上，半径同样由 RSSI 决定，参与同一套力导向聚类 |
| 列表视图 | 强度/时间线/分类三个视图自动包含星闪设备（复用同一份 sightings 数据） |
| 筛选 | 「仅 Wi-Fi / 仅 BLE」增加「仅星闪」选项，逻辑与现有单选一致 |
| 详情页 | 字段与 BLE 对齐：名称、地址、信号强度、设备类型、出现次数；额外展示 `isConnectable` |
| 标签配置 | 名称/地址/类型/强度/频段开关**自动对星闪生效**，无需新增设置项 |
| 关注目标 | 星闪设备可加入关注列表，通知逻辑复用 |
| 权限提示 | 复用同一套受限卡片与说明框，文案替换为「星闪」 |
| 特征库 | 星闪广播同样送入签名引擎匹配 |

**关键点**：所有这些「自动生效」都建立在 4.1 的接口复用上 ——
只要扫描器把数据喂进同一份 `sightings`，上层全部无需改动。

## 七、能力门控与降级（必须有）

星闪有硬件门槛，必须优雅降级，而不是报错或显示空数据：

| 情况 | 探测方式 | 表现 |
|---|---|---|
| 芯片不支持 | `manager.isNearLinkSupported()` 为 false，或扫描抛 `801` | **完全不显示星闪相关 UI**，也不申请权限 |
| 星闪未开启 | `manager.getState()`，或扫描抛 `36100003` | 在扫描分区显示「星闪未开启」，与现有「蓝牙未开启」同款提示 |
| 未授权 | `checkAccessTokenSync` | 复用受限卡片，按钮申请 `ACCESS_NEARLINK` |
| 权限被永久拒绝 | 请求返回拒绝 | 复用「系统不会再弹出授权窗口」说明框 |

> **本机需实测**：MatePad Mini (MLR-AL10) 是否支持星闪，直接决定这个功能能否在现有设备上验证。
> 若不支持，需要在支持星闪的机型上验证，或至少完成代码与编译验证并如实说明。

## 八、关于星闪测距（`fusionConnectivity.ranging`）

星闪测距理论上能给出**真实距离**，比 RSSI 估算可靠得多，是本应用真正的差异化点。
但它需要建立 ranging 会话，与本应用「只接收、不连接」的原则存在冲突。

**建议**：暂不纳入。若后续要做，必须：
1. 明确告知用户这会**主动与目标建立会话**，与被动监听模式区分开；
2. 作为独立模式（如「单信号跟踪模式」）的一部分，而不是混进被动雷达；
3. 重新评估隐私协议措辞。

**这个取舍需要你决定。**
