# 电波足迹 · 全功能审计报告

> 审计方式：逐个页面、逐条 UI 动作追踪到实现；对每个设置项检查「是否真被消费」；
> 对所有 `RadioKind` 分支检查是否漏掉星闪；对 `@Builder` 参数做响应式风险扫描。
> 日期：2026-10-08

## 一、审计结论

**没有发现「点了完全没反应」的假按钮** —— 所有 `onClick` 都有真实实现。

但发现了 **5 处真实的「部分实现」**（功能能进、但某个方向不通）、**1 处死设置**。
**全部 5 处已修复**；死设置按用户决定保留不动。

> **一处结论更正**：初版把 OUI 判为「未移植」，实际是采信了过期 TODO 未做验证。
> 真实缺口是另一个位置（厂商名从未挂到观测上），详见第二节 B。

## 二、已修复的问题

### 🔴 1. 星闪签名规则无法在保存/加载中存活（数据损坏，已修）

**性质**：部分实现 + 数据完整性缺陷。

模型 `SignatureRule.radio` 支持 `RadioKind.NEARLINK`，匹配引擎也正确
（`rule.radio !== context.kind` 精确比较），但：

| 环节 | 原实现 | 后果 |
|---|---|---|
| 序列化 | `radio === WIFI ? 'WIFI' : 'BLE'` | 星闪规则**被写成 BLE 规则** |
| 解析 | `signatureRadioKindOf` 不认 `NEARLINK` | 星闪规则**变成「任意种类」** |
| 规则身份键 | 同样只有 WIFI/BLE | 星闪与 BLE 规则**被当成同一条去重** |

**修复**：新增 `SignatureRule.radioTag()` 作为唯一的三态映射出口；
`signatureRadioKindOf` 识别 `NEARLINK` / `NEAR_LINK`；身份键改用 `radioTag()`。
补 2 个回归测试（往返保真 + 不跨种类命中）。

### 🔴 2. 签名规则编辑器无法选择星闪（已修）

规则的单选只有 `0=任意 / 1=Wi-Fi / 2=BLE`，且回显把星闪**显示成「BLE」**。
已增加「星闪」选项，回填/提交/显示三处都按三态处理。

### 🟠 3. 「实时模式」保存了但重启不恢复（已修）

**性质**：部分实现。

`switchLiveMode` 会持久化（`updateLiveMode`），但**读回来的值进错了结构体**：
- 根页面把设置读进自己的 `liveMode` 字段；
- 实时页用自己的 `mode` 字段渲染，初始恒为 `RADAR`；
- 两者之间**没有任何传递**。

**用户可见后果**：切到「强度/时间线/分类」→ 重启 → 永远回到「雷达」。
已加 `@Prop savedLiveMode` 并传入，实时页启动时应用。

### 🟠 4. 后台长时任务「静默保活」（已修）

`BackgroundTaskManagerFacade.startContinuousTask(title, content)` **收了文案却完全没用** ——
只调 `startBackgroundRunning`，从不发通知。
鸿蒙官方设计要求长时任务必须伴随用户可见通知；
原实现既不规范，用户也无从知道应用还在后台跑。

**修复**：新增 `publishStateNotification()`（固定 ID，覆盖更新）；
应用启动即发布运行状态通知并每 3 秒刷新；启动时按设置同步长时任务。

### 🟡 5. 三条假告警（已修）

- `停止后台长时任务失败: [object Object]` —— 异常未转文本，且 **`9800005`
  「本来就没申请过长时任务」被当错误**（默认设置就是关闭，每次启动必报）。
- 通知未授权时每 3 秒刷一条错误日志。

## 三、仍存在的问题

### ⚠️ A. `darkMode` 是死设置

`AppSettings.darkMode` 被持久化、备份、导出，**但全仓库没有任何消费者**。
外观实际由 `ngfThemeManagerFacade` 控制（设置页的「外观主题」三按钮）。

**性质**：遗留死代码 + 一个永远不会被使用的持久化键。
**建议**：移除该字段与键；或在设置页明确它已由「外观主题」取代。
**现状**：无用户可见影响，未改动。

### 🔴 B. OUI 厂商名虽能查询，但从未被挂到观测上（已修）

> **更正**：本节初版结论写错了。我当时采信了 `FieldwatchDomainService.ets:72` 的一条
> `TODO(F11-vendor)` 注释，**没有去验证实现**。实际查证后发现该注释已过期 ——
> 就在这行注释的下方两行，代码**已经在用厂商名匹配了**。
> **教训：TODO 注释是意图记录，不是事实陈述，必须对照实现验证。**

**实际状态（查证结果）：**

| 环节 | 状态 |
|---|---|
| OUI 名称库 | ✅ 完整 —— `rawfile/lookups/radiodb.bin`，**MA-L 39995 条 / 34781 个名称** |
| 查询实现 | ✅ 完整 —— `vendorForOui24()` 二分查找 + 字符串池 |
| 自检 | ✅ 通过 —— `00:1B:63 -> Apple, Inc.` / `公司 0x004C -> Apple, Inc.` |
| 筛选匹配厂商名 | ✅ 已实现 —— `ouiOk` 同时匹配 MAC 与厂商名 |
| **`facts.manufacturer` 填充** | ❌ **从未被赋值** —— 所有构造点都传空串 |

**真实缺口是这个**：`RadioFacts.manufacturer` 一直是空串，因此
**依赖它的地方全部静默失效**：

- 候选引擎的厂商排除（`isChipModuleVendor` / `isSkippedOuiVendor`）永远拿到空串；
- 详情页看不到厂商；
- 导出（CSV / JSONL）没有厂商列。

**已修**：

1. `FieldwatchApplication.attachVendor()` —— 在 `ingest()` 入口把 OUI 厂商名补到观测上。
   放在入口可覆盖全部信号源与全部路径（含定位标记分支与旧记录恢复分支）。
2. **详情页**新增「厂商」行（查不到厂商时不占行，避免满屏「未知」）。
3. **导出** CSV 增加 `manufacturer` 列（紧随 `name`），JSONL 增加 `manufacturer` 字段。
4. 清理了那条过期的 TODO 注释，替换为对当前实现的准确描述。
5. 补端到端测试：构造合成 OUI 库，验证**按厂商名能命中、按 MAC 能命中、按不存在的厂商不命中**。

## 五、系统性风险扫描结果

- **`@Builder` 按值参数**：扫全部 5 个页面，**无新增风险点**。
  仅剩 `buildSizeStepper(label, isFont)` —— `isFont` 是每个调用点的常量，
  且数值在 builder 内读 `@State`，安全。
- **设置键读写配对**：17 个键**全部有读有写**（`darkMode` 有读有写但无人消费，见上）。
- **空 `onClick`**：全仓库 0 处。
- **`RadioKind` 分支漏星闪**：本轮已全量修复（持久化 ×2、导出 ×4、状态归档、候选、配色、规则序列化 ×3）。
