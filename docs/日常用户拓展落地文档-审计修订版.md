## 一、P0（约 2 周）：日常模式 + 找东西 + 提醒策略 + 商店并行

### 1. 日常模式框架（新建，小）

## 附录 A：找东西（P0-2）关键设计细节

### A.1 系统已配对 / 已连接设备能不能用来认人

| 问题 | 结论 |
|---|---|
| 能否拿到系统已配对蓝牙设备来认人？ | **能，而且是本功能的主锚**。`connection.getPairedDevices()` 返回已配对设备地址数组；另有 `getRemoteDeviceName(地址)`、`getRemoteDeviceClass(地址)` 可补名称与设备类别。只需 `ACCESS_BLUETOOTH`，已在册 |
| 能否知道某台设备当前正连着手机？ | **能**（按 Profile 查）。A2DP/HFP/HID 等 Profile 对象提供已连接设备查询与 `connectionStateChange` 事件；连接状态可让目标列表显示「正在使用中」并免认领 |
| 能否拿到 Wi-Fi 已连接 / 曾连接信息？ | **当前连接能，曾连接列表不能**。`wifiManager.getConnectedInfo()` 给当前 AP 的 SSID/BSSID/信号/频段；官方 wifiManager 公开接口里没有「已保存网络列表」，只有本应用自己添加的候选配置可查。对「找东西」影响不大：Wi-Fi 目标只做「找路由器」，BSSID 长期稳定 |
| 能否拿到星闪已配对列表？ | **未证实，按「拿不到」设计**。星闪是华为专有 Kit，公开镜像文档里未见配对列表接口；仓库现用 `manager/scan` 只有扫描。开工前在本机 API 26 SDK 的类型定义里核实一次（见 V5），v1 星闪目标一律走「现扫现认」 |

关键官方事实：**`getPairedDevices()` 给的不是真实 MAC，而是系统分配的虚拟 MAC**。配对关系存续期间该地址不变；取消配对、或蓝牙关闭后重新获取，地址可能变更；如需持久化标识，可用 `access.addPersistentDeviceId` 为设备生成持久 ID。**因此身份设计不能只存一个地址了事**（见 A.2）。

### A.2 身份档案：认领到底存什么

新增领域模型 `domain/FieldwatchOwnDevice.ets`（或扩 WatchTarget 字段，二选一，推荐新建模型、WatchTarget 只存引用），每条档案字段：

| 字段 | 来源 | 用途 |
|---|---|---|
| `persistentId` | `access.addPersistentDeviceId`（认领时对目标调一次） | 跨蓝牙开关/重扫的持久锚 |
| `virtualAddress` | getPairedDevices / 扫描 deviceId | 当前配对期内的快速匹配锚 |
| `displayName` | getRemoteDeviceName / 广播名 / 用户改名 | 展示与搜索 |
| `deviceClass` → 图标 | getRemoteDeviceClass / 签名分类 | 列表图标（复用现有 DeviceTypeIcon + ClassLabels） |
| `fingerprint` 快照 | 认领那一刻的广播：名称、厂商数据键、服务 UUID 集、命中 signatureId | 锚失效时的兜底匹配 |
| `lastSeenAt / lastLocation` | 观测管线回写 | 「上次见到」 |

**匹配管线**（`domain/FieldwatchOwnDeviceMatcher.ets`，纯逻辑 + 单测）：实时 Sighting 进来后按序判定 — ① 地址直配（virtualAddress/persistentId 命中，最高置信）→ ② 指纹打分（名称全等 +3、厂商数据键命中 +2、服务 UUID 集包含 +2、签名命中 +2，≥5 分认作同一台）→ ③ 都不过则不是自有设备。阈值集中成常量，真机阶段用自有设备组调。阈值宁高勿低，档案卡上保留「这不是我的设备」一键纠错，纠错即把该指纹拉黑名单（档案加 `denyFingerprints` 数组）。

### A.3 寻找向导：直接复用 Hunt 的全部家底

- 状态机现成：`huntCue()` 已产出七态（VERY_CLOSE / CLOSER / FURTHER / SAME / WAITING / QUIET / GONE），判定用 2 秒近窗 vs 3.5–8 秒远窗的均值差（阈值 3 dB），日常文案与七态一一映射即可，**判定逻辑零重写**。
- 盖革滴答现成：滴答间隔映射（-40dBm 最急、-90dBm 最缓，90–1400ms），安静/消失态自动静默；`FieldwatchHuntFeedback.ets` 的声音与震动都已封装好。
- 「非常近」阈值现成：`HUNT_VERY_CLOSE_DBM = -45`（口袋/手持/同一背包量级）— 日常文案「就在你身上或包里，先摸一摸」正好落在这个量级上。
- 会话记录现成：HuntRecord/HuntStats 可直接给「找到了」收尾与历史用。
- 新写的只有页面 `pages/fieldwatch/FieldwatchFindPage.ets`，消费 HuntSession + HuntCue，做三件 UI 的事：大号热度可视化（用 cue + 近窗均值，不显示 dBm）、状态文案、声震开关。原专业 HuntPage 保持不动。

### A.4 简单好用的硬指标（上线门禁）

- 首次认领（已配对设备）：从日常首页起 **≤3 次点击**（找东西 → 点设备名 → 进入向导，认领与进入合并为一步）。
- 再次找已认领设备：**≤2 次点击**（首页卡片 → 点设备 → 已在向导中自动开扫）。
- 找的过程中：**零决策点**，直到「找到了」为止用户不需要做任何选择；声震开关是唯一可选项且默认全开。
- 状态文案每态一句人话（进资源文件走现有 i18n 方式）：WAITING 超 10 秒无任何包 → 自动展开排查卡（最多 3 条，按目标类型生成）；QUIET → 「暂时听不到它了，可能被金属/墙体挡住，换个方向慢慢走」；GONE → 不说「丢失」，说「它不在附近，先看看上次见到是几点、在哪」并给 lastSeen 卡；VERY_CLOSE → 整屏变色 + 长震 + 大字「就在附近！」。
- 防呆：同名多台时用「拿起你的那台晃一晃」确认法（短窗信号方差突增的那台自动高亮打勾）；任何档案卡长按有「这不是我的」。
- 无障碍：热度不能只靠颜色 — 颜色 + 字号 + 声震三通道并行；全部文案过一遍大字体模式不溢出。
- 简单性验收：术语 grep 验收（日常页资源文案中不得出现 RSSI/dBm/MAC/广播/签名等词）、点击预算实测、找一位没用过本 App 的人实测「找耳机」全流程不求助完成。

### A.5 真机验证清单（开工第一周内清掉，决定设计分支）

| # | 问题 | 验证方法 | 通过标准 / 分支 |
|---|---|---|---|
| V1 | 扫描的 deviceId 与 getPairedDevices 的虚拟地址是否同值 | 拿已配对耳机，打印两边地址逐字比对（临时调试页或日志） | 同值 → 地址直配成立；不同值 → 指纹兜底升为主路径，地址直配只用于配对名单内部 |
| V2 | `addPersistentDeviceId` 的持久性边界 | 认领后依次：关开蓝牙、重启手机、隔天再扫 | 三种情况都能找回同一 persistentId 才把它当主锚，否则降为辅助 |

### A.6 明确不做（找东西）

不发起任何配对/连接动作（认领只读系统名单，与本 App「只接收不连接」底线一致 — `getPairedDevices` 等都是只读查询，不在此限）；不承诺 BLE 连接态；不做后台常驻寻找；星闪不做导入（V5 有惊喜再说）。
