> **范围界定（2026-10-08 补）**：本矩阵只衡量 **Fieldwatch 1.1.17 → HarmonyOS 的移植对等性**。
> **鸿蒙专属增项另计**：星闪（NearLink）全链路、服务卡片、流转、多窗口 —— 这些在原版 Android 上不存在，
> 不属于移植完成度，不应混入本矩阵的判定（此前混淆过一次，导致误判「移植已完成」）。
>
> **⚠️ 本矩阵的判定方法警告（2026-10-09 补）**：**存在性检查会系统性误判。**
> 本轮用脚本扫描「定义了但从未被调用」的方法，发现 `shareCurrentCsv` / `shareCurrentJsonl` /
> `shareCurrentGpx` / `shareCurrentKml` / `shareCurrentWigle` / `saveCurrentCsv` / `saveCurrentJsonl` /
> `sharePath` / `shareCandidates` / `exportCatalogText` **共 10 个方法调用数为 0** ——
> 它们**看起来就是「分享/导出已实现」**，但没有任何界面调用它们。
> 真正的导出走的是 `shareExport` / `saveExportAs`（Reports 页 2484 / 2490 行）。
>
> **若按「代码里能找到」判定，这 10 个方法会让「分享导出」这一项直接通过。**
> 这正是本矩阵要求「逐项核对是否真的生效」的原因。已删除这批死代码，消除误判源。
>
> **因「严格离线」约束而排除（2026-10-09 补）**：交付范围明确为
> *「严格离线，网络仅用于用户主动发起的目录更新」*。因此下列**原版确实存在、但不移植**：
>
> | 原版功能 | 清单位置 | 为何排除 |
> |---|---|---|
> | **TAK / CoT UDP feed** | §12.5 全节、§12.6「暂停 TAK / CoT feed」 | 是 UDP 网络外发（含 LAN 组播 239.2.3.1:6969 与自定义主机），与离线约束直接冲突 |
> | **在线反向地理编码（地点名称）** | §12.4「地点名称」、§13「地点名称可能通过系统地理编码服务获取」 | 依赖系统地理编码服务，需联网；离线时无法提供 |
>
> **这不等于这两项「已实现」或「不重要」，而是经用户确认的交付边界之外。**
> 若日后要纳入，应作为独立增量立项，而不是回填进本矩阵充数。
>
> **`onlineLookup` 相关的联动项**（§12.6「隐藏街道名称」）同样随之不适用 ——
> 本应用不产生地点名称，也就没有「隐藏」的对象；其余隐私项（MAC 尾部掩码、坐标掩码）已实现并有单测。

## 不得替代的证据

- 构建成功不代表运行成功。
- 自动点击成功不代表页面状态或业务效果正确。
- BLE 扫描成功不代表 Wi-Fi、后台或通知能力已完成。
- 系统门面调用成功不代表对应系统 UI 已真实出现。
- `hvigorw test` 输出 `BUILD SUCCESSFUL` 不代表测试通过；2026-10-06 实测失败用例不会使构建失败，必须检查 `> hvigor ERROR: Error in ` 行。
- 在 U30 热点环境取得的 Wi-Fi 成功结果不能外推为普通路由器主验收通过。
- **改主题必须同时改两处**：`setThemeOverride` 只写 AppStorage；`$r('app.color.*')` 的深/浅解析取决于**应用颜色模式**（`setColorMode`）。只改前者会让一半页面留在浅色目录。
- ArkUI 保留属性名会静默冲突：`enabled`、`size` 都不能用作自定义组件的 `@Prop` 名。
- 未指定背景的 `Button` 会使用系统强调色（蓝），必须显式上色。
- 单元测试的手写样本必须复刻**真实序列化器的输出形状**：2026-10-06 真机发现内置 stock 目录含 437 个 `"radio": null` 及上千个 `length/scale/unit/when: null`，而测试样本一律「省略键」，因此只判 `undefined` 的解析器在单测里全绿、在真机上整包抛异常导致特征库为空。手写样本必须包含显式 null。
- 导航必须用仓库已验证的 `pushPathByName` + `HdsNavDestination` 根节点：`pushPath({name,param})` 会触发系统路由查找并失败（`can't find name in config file`），页面渲染为空节点。
- 新增字段后必须回头检查所有「按字段逐个拷贝」的持久化代码：2026-10-06 扩到 20 类签名后，`loadFilterPreset` 仍只白名单了 4 类，预设会静默丢类别；`loadWatchlist` 仍按 `deviceKey.length === 0` 过滤，导致签名级关注重启即丢。两处都是扩展时漏改的序列化路径。
- 只读一遍源码不能代替对真实数据的审计：2026-10-06 对 stock 目录做契约审计时发现两个只在真实数据下暴露的解码缺陷（首字段门控失败会丢掉整条签名的全部字段，影响 6 条签名；`bits` 类型忽略 `scale`，影响 ruuvi 的 tx_power）。两者都已修复并加了回归用例。

## 2026-10-12 隐私缺陷修复：隐私模式下 `key` 列泄漏完整 MAC

**缺陷（真机发现）**：开启「隐私模式」后导出 JSONL，`address` 已按策略脱敏为 `F0:07:1C:**:**:**`，但同一行的 **`key` 字段仍是完整 MAC** ——
```json
{"key":"ble:F0:07:1C:43:04:07","kind":"ble","address":"F0:07:1C:**:**:**", ...}
```
`key` 形如 `ble:<MAC>`（Wi-Fi 为 `wifi:<BSSID>`），与 `address` 是同一标识；CSV 的首列同样如此。既有单测只断言「输出里存在 `**:**:**`」，因此**完全无法发现这一列泄漏**。

**修复**：`FieldwatchExportSerializer` 的 `serializeCsv` 与 `serializeJsonl` 对 `key` 套用与 `address` 相同的 `maskAddress(key, privacyMode)`（`maskAddress` 按分隔符切分，`ble:F0:07:1C:43:04:07` → `ble:F0:07:1C:**:**:**`，保留前缀与厂商段）。GPX / KML 不含地址，WiGLE 走 `address`，均无需改动。

**测试**：`FieldwatchDomain.test.ets` 新增用例 `masks the embedded address inside the key column of csv and jsonl` —— 断言隐私模式下 CSV 与 JSONL 均**不含任何完整 MAC**（正则 `[0-9A-F]{2}(:[0-9A-F]{2}){5}`），且关闭隐私模式时恢复完整地址。

**测试门禁的重要事实（变异校验所得）**：把该用例断言临时反转后运行 `hvigorw test`，日志出现
`> hvigor ERROR: Error in masks the embedded address inside the key column of csv and jsonl, expect true, actualValue is false`，
但**退出码仍为 0、仍打印 `BUILD SUCCESSFUL`**。即断言失败只以 `Error in <用例名>` 行体现 —— 这正是「BUILD SUCCESSFUL 不等于通过、必须检查 `Error in` 行」的硬证据。还原后复跑：`ERROR_LINES=0`。

**真机复验（API26，隐私模式开）**：重新导出 JSONL → `fieldwatch-log-2026-10-12-06-55-36.jsonl`（23618 字节，**114 行**）：每行 `key` 与 `address` 均为 `2C:13:7C:**:**:**` 形式，**含完整 MAC 的行数 = 0**，脱敏行数 = 114。修复前同一路径的样本 `fieldwatch-log-2026-10-12-06-37-51.jsonl` 中 `key` 为完整 MAC。

## 2026-10-12 【严重】候选特征「添加到目录」把内置 611 条签名从落盘文件中抹掉（已修复）

**现象**：在记录页「特征目录」卡片点「**添加到目录**」后，特征库从 **611** 变成 **显示 4 / 4 · 签名总数: 4**；沙箱文件 `/…/files/fieldwatch/signatures.json` 从 2258081 字节缩到 **1656 字节**，内容只剩 4 条 `user-*` 用户签名。**重启后仍为 4 条**（不是显示问题）。

**根因**：`FieldwatchApplication.addCandidateToCatalog`（当时 `:1734`）落盘时传的是**过滤掉 builtIn 的列表** ——
```ts
this.catalogRepository.save(this.state.signatures.filter((item) => !item.builtIn)); // 只写用户签名
```
其余调用点都是 `save(this.state.signatures)`（全量）。于是文件里内置 611 条被抹掉，但 `catalogVersion` 仍写着当前 stock 版本 102 → 下次启动 `stockVersion > savedVersion` **不成立** → 不再合并 stock；`ensureCatalogLoaded` 又只判断 `signatures.length > 0` → 直接返回。**三重条件叠加导致内置目录永久丢失**。

**修复（三处）**：
1. `addCandidateToCatalog` 改为落盘**全量** `this.state.signatures`（与其它调用点一致），并记录目录总条数。
2. `loadBundledCatalog` 增加**损坏识别**：当「保存的目录一条内置项都没有、而 stock 有」时按损坏处理，强制叠加 stock 并落盘（可修复已被写坏的设备）。
3. `ensureCatalogLoaded` 的就绪判定从「长度 > 0」改为「**长度 > 0 且含内置项**」，否则重试 `loadBundledCatalog` —— 否则损坏目录永远不会触发上面的修复。

**真机验证（同一台设备，先复现再修复）**：
| 阶段 | 沙箱文件 | 内置 / 用户 | 界面 |
|---|---|---|---|
| 缺陷复现 | 1656 B | 0 / 4 | 显示 4 / 4 |
| 装上修复并启动（自动修复） | 2259583 B | **611 / 4** | 显示 **615 / 615** |
| 再次「添加到目录」 | 2259968 B | **611 / 5** | 显示 **616 / 616** |
| 重启后复查 | 同上 | **611 / 5** | 持久正确 |

**遗留**：为验证流程产生的 **5 条测试用户签名**（`CMCC` ×2、`Company 0x027D 10`、`UUID FE95`、`Vendor IE 000005`）仍在目录中。清理路径：**特征库 → 更多 → 恢复默认目录**（代码注释明确其语义为「只保留内置 stock，清除用户新增与编辑」，且会先弹确认）。本轮多次尝试用注入点击驱动「更多」菜单**未能命中**（菜单在页面每秒刷新下会自动关闭，且菜单项点击不可靠），故保留给用户一键清理。
