# 主动扫描授权与隐私体系设计（App 内 ACL）

> 修订记录：v2（2026-10-27 晚，用户澄清后重组）。
> v1 的写法重心偏了：花了大篇幅讲鸿蒙系统的 ACL 权限申请流程，容易让人误以为本设计要走系统 ACL。
> **澄清：本文的 ACL 是 App 内机制，不是鸿蒙系统的 ACL 流程，本 App 也不申请系统 ACL。**
> 它只是借用 ACL 的思想——主体、权限、客体三元组，默认拒绝、显式授权、逐项可审计——
> 在 App 内部给一切主动扫描行为设关卡。v1 中关于系统 ACL 的章节已删除，只保留一句动机说明（见第 1.3 节）。
>
> 决策背景（不变）：局域网主动探测从“暂不做”改为**在严格授权与隐私体系下做**。
> 《日常功能实测反馈四项完善方案.md》3.2 与附录 A.2 / B 的“暂不做”以本文为准更新：
> 不是无条件重启主动层，而是只有本文的 ACL 引擎、任务绑定、范围硬约束、隐私体系全部落地后，
> 主动能力才允许进入安防扫描任务；任一环节缺失，主动入口保持关闭。
> 本文档是设计稿，不是实现；实现前先跑第 10 节阶段一的真机验证清单，验证结论写入实施汇报。

## 1. 先定概念：什么是“主动”，什么是 ACL

### 1.1 “主动”的判定规则

一句话：**凡是向非固定服务端点发送报文或发起连接尝试的，都算主动。**

- 固定服务端点只有两个：特征库更新源、反馈中心（`feedback.manxia.top`），两者皆为 HTTPS 固定域名。
- 除此之外，任何对外发送都算主动，不论报文多小、目标多近：一次 TCP connect、一次 UDP 探测、
  一次组播 Probe、一次 M-SEARCH，全部是主动。
- 这条规则是封闭的：未来出现新的发送行为，先按本规则判定，再决定进不进 ACL 表；
  判定为主动的，不登记就不得调用（见 2.4 默认拒绝）。

### 1.2 被动 / 主动对照表（判定有争议时以此为准）

| 行为 | 定性 | 说明 |
|---|---|---|
| WiFi 系统扫描（SSID / BSSID / 频段 / 信号） | 被动 | 只读系统扫描结果，不发探测包 |
| BLE / 星闪广播扫描 | 被动 | 只收广播，不连接 |
| 组播宣告监听（SSDP NOTIFY / mDNS 宣告） | 被动 | 纯接收；但原生组播成员 API 待实测（见第 8 节），验证失败则此项不可用 |
| M-SEARCH、ONVIF WS-Discovery Probe | **主动** | 主动发送查询报文，必须走 ACL |
| TCP connect、UDP 探测 | **主动** | 向目标发起连接 / 报文，必须走 ACL |
| RTSP / ONVIF / HTTP 握手、二进制魔数比对 | **主动** | 向目标发协议报文，必须走 ACL |
| GATT 连接读名 | **主动** | 且本 App 不做（违背只接收不连接的底线，见第 3 节排除项） |
| WOL 唤醒包（未来能力） | **主动** | 尚未登记，登记后方可排期（见第 3 节末） |

### 1.3 为什么 App 内必须自设关卡（仅存的系统侧事实）

主动发包走 `@ohos.net.socket`，所需权限 `ohos.permission.INTERNET` 是系统授予、
安装时自动给、不弹窗。系统层面不区分“向固定服务器拉数据”和“向内网任意主机发探测包”，
同一个权限两种行为全放行。**所以关卡只能设在 App 内**——这就是本文 ACL 存在的全部理由，
与系统 ACL 流程无关。

## 2. ACL 模型：App 内管理主动扫描的完整机制

### 2.1 三元组

- **主体**：任务 / 功能 / 入口。不是“用户”也不是“设备”，而是 App 内的任务：
  安防扫描、WiFi 体检、找东西，未来新增任务默认没有任何主动权限。
- **客体**：能力 + 目标范围。能力是 A1–A7（第 3 节），目标范围是当前已连 WiFi 网段内的主机
  （约束见第 5 节）。能力与目标缺一不可：有能力无范围不放行，有范围无能力也不放行。
- **权限**：允许 / 拒绝。二值，没有“部分允许”——某能力要么整项授权，要么不授权；
  目标范围、速率、数据处理是授权的附加条件，不是第三种权限值。

### 2.2 ACL 表

ACL 表是本地数据（可查看、可导出审计、可一键关闭），每条记录：

| 字段 | 含义 |
|---|---|
| 能力 id | A1–A7（第 3 节） |
| 主体 | 哪个任务可用（第 4 节） |
| 目标范围 | 允许的目标集合 + 排除项（第 5 节） |
| 风险等级 | 低（枚举类 A1 / A2 / A6）/ 高（协议握手类 A3 / A4 / A5 / A7）；高风险能力弹窗文案须额外标明“将与目标设备建立协议交互” |
| 数据处理 | 该能力允许记录什么、不允许记录什么（第 7.2 节） |
| 速率 / 并发 / 超时 | 单目标超时、并发上限、总时长上限、重试策略（不重试） |
| 授权粒度 | 仅本次扫描会话；会话结束即失效；设置页可手动重开 |
| 告知文案 key | 弹窗四要素（能力、范围、暴露面、数据去向）的文案键 |
| 审计字段 | 每次执行记：时间、任务、能力、目标范围、结果数、成功 / 失败 |
| 表版本 | ACL 表随应用版本走；审计记录记表版本，事后可追溯当时按哪版规则放行 |

### 2.3 ACL 引擎：唯一放行点

任务代码**不直接创建 socket**，一律向 ACL 引擎申请（主体 + 能力 + 目标），引擎按顺序核对：

1. 任务绑定：该任务是否被允许用该能力（第 4 节）——不符直接拒绝。
2. 会话授权：本次扫描会话是否已获用户确认——未确认直接拒绝。
3. 目标范围：目标是否在允许集合内且不在排除项内——越界直接拒绝。
4. 速率 / 并发：是否超上限——超限排队或拒绝，不静默放行。
5. 审计记账：放行与拒绝都记审计；拒绝本身也是一条可查记录。

引擎是 App 内唯一的 socket 创建入口。任何旁路（任务代码直接建 socket、
复用固定源网络客户端发内网请求）都视为违规实现，验收时以静态检查拦截（见 2.4）。

### 2.4 治理规则：让 ACL 表永远等于实际行为

- **默认拒绝**：未登记的能力一律拒绝调用；新增发送行为先登记、后实现，顺序不得颠倒。
- **失败关闭**：授权状态不明、目标范围推导失败、审计写入失败时，引擎拒绝放行，
  不得“先放行、后补记”。
- **静态检查门禁**：除 ACL 引擎模块外，代码中不得出现 socket 创建调用；
  每版提交前以 grep 核对（`TCPSocket / UDPSocket / constructTCPSocketInstance /
  constructUDPSocketInstance` 的命中只允许出现在引擎模块与注释中）。
- **每版复核**：每次发版前复核 ACL 表与实际调用是否一致（表里有的是否都还在用、
  实际调用的是否都在表里），复核结论写进版本汇报。
- **表版本化**：ACL 表结构变更（新增 / 删除能力、改目标范围）须同步更新表版本与文档，
  不得只改代码不改表。

## 3. 能力全表（完整覆盖全部主动方法）

| 能力 | 对应主动方法 | 风险 | 允许的操作 | 明确不做的事 |
|---|---|---|---|---|
| A1 网段存活探测 | ARP 扫网段的**替代实现**（ARP 无 API，见第 8 节） | 低 | 对网段内主机做 TCP connect（常见端口）与 UDP 探测，判定存活 | 不发 ARP；不拿 MAC；不对存活主机做任何超出 A2 的事 |
| A2 端口探针 | 端口探针 | 低 | 白名单端口表：80、443、554、8000、8080、8443、8899、1935、3702、37777、34567、9000、1900、5353；只记 open / closed | 不读横幅全文；不扫白名单外端口；不扫公网 |
| A3 RTSP 探测 | RTSP OPTIONS / DESCRIBE | 高 | 只取 Server 标识类别与 SDP 编码类型，用于厂商分类 | 不存流地址；不拉流；不试口令 |
| A4 ONVIF 探测 | WS-Discovery Probe + GetServices / GetCapabilities | 高 | 组播 Probe（`239.255.255.250:3702`，NetworkVideoTransmitter）+ 单播回包；仅取设备类型与服务清单 | 不调 GetStreamUri；不拉流；不调需认证的配置接口 |
| A5 HTTP 横幅 | HTTP 横幅 / 管理页特征 | 高 | 只取 Server 头类别，用于厂商分类 | 不爬管理页；不试默认口令；不登录 |
| A6 服务发现查询 | mDNS / SSDP 主动查询（M-SEARCH） | 低 | 仅服务类型与设备描述类型字段（如 UPnP `DigitalSecurityCamera:1` 方向） | 不做组播监听（除非阶段一验证通过）；不存完整设备描述文档 |
| A7 厂商二进制魔数 | 大华 37777、Reolink 9000 Baichuan、XMEye 34567 等私有协议握手字节比对 | 高 | 只比对魔数字节，命中即厂商分类 | 不发后续载荷；不进入会话；不利用协议漏洞 |

**排除项（ACL 表之外，任何任务不得申请）**：弱口令 / 默认口令尝试、RTSP 拉流、
ONVIF GetStreamUri 拉流、GATT 连接读名、漏洞利用、配置修改、登录尝试、公网目标、
历史网络、后台常驻扫描、目标拒连后的重试爆破。

**未来能力登记区（登记后方可排期，当前不得实现）**：WOL 唤醒包（向指定主机发 Magic Packet，
主体仅限“我的设备”任务，目标仅限用户已认领设备）；其他未来发送行为按 1.1 规则判定后在此登记。

## 4. 任务绑定（最小化：哪个任务能用什么）

| 任务 | 可用能力 | 理由 |
|---|---|---|
| 安防扫描 | A1–A7 全部 | 任务本身就是“找出可疑联网设备”，需要完整枚举 + 协议分类 |
| WiFi 体检 | 仅 A1 | 体检只需要“当前网络里有哪些存活主机、与当前 AP 的关系”，不需要摄像头协议分类；端口与协议能力不对体检开放 |
| 找东西 | 无 | 找东西是认领已发现的蓝牙 / WiFi 设备，保持纯被动；主动探测对其无收益，只增风险 |
| 日常页 / 图鉴 / 记录 / 设置 | 无 | 非任务页不触发任何主动能力 |
| 未来新增任务 | 无（默认） | 新任务如需主动能力，须在 ACL 表中为其新增主体条目并经过第 2.4 节的登记流程，不得继承其他任务的授权 |

## 5. 目标范围硬约束（代码级，不是文案）

- 仅当前已连 WiFi 的网段：由 `linkAddresses` 前缀长推导；推导失败时，
  降级方案（二选一，实施时定死并写进汇报）：（a）按本机 IP + /24 假设并在 UI 明示假设；
  （b）拒绝执行并提示“无法确定网段”。不得静默按猜测的网段扫描。
- 排除本机地址与网关地址（网关是路由器，探测它无分类收益且更敏感）。
- 排除公网地址、排除历史 SSID 网络、排除蜂窝网络（仅 WiFi 下可用）。
- 并发上限、单目标超时、总时长上限在实施时定死（建议起点：并发 16、单目标 800ms、
  总时长 60s，实测后调）；目标拒连 / 超时不重试；扫描中用户取消即关全部 socket。

## 6. 授权流程（任务级通报）

1. 用户在安防扫描页点“开始主动扫描”（被动扫描与主动扫描是两个分开的入口与按钮，
   不得把主动能力藏进被动扫描的默认流程）。
2. 弹窗通报四要素，缺一不可：**本次将用的能力**（A1–A7 逐项列出，非笼统的“网络扫描”；
   高风险能力额外标明“将与目标设备建立协议交互”）、**目标范围**（当前 WiFi 的 SSID + 网段）、
   **会暴露什么**（见 7.1）、**数据去向**（只存本机、不上传、可删除）。
3. 用户确认后授权仅对本次扫描会话有效；会话结束（完成 / 取消 / 切后台 / 断网）
   即失效，下次重新通报。
4. 拒绝时零发包：弹窗拒绝后不得有任何 socket 创建（验收时以日志抽查为准）；
   拒绝只针对本次，入口保留；设置页提供“关闭该能力”——关闭后需手动重开，
   避免一次误点永久失去功能，也避免反复弹窗骚扰。
5. 审计：每次扫描（包括被拒绝的申请）记一条本地审计记录，设置页可查、可删；
   审计记录记 ACL 表版本。

## 7. 隐私处理与防自身信息暴露体系

### 7.1 暴露面清单（向用户诚实列出，弹窗文案照此写）

- 本机 IP 会出现在目标设备 / 路由器的日志里——主动扫描无法做到“不留痕”，
  这是与被动扫描的本质区别，弹窗必须明说。
- 探测报文特征（端口序列、ONVIF Probe、M-SEARCH）可被识别为扫描行为；
  同网段监听者能看到组播 Probe。
- 扫描结果若上传，会暴露用户所在网络与家庭设备清单——因此结果绝不上传（7.2）。
- 以下**不会**暴露：本机设备名 / 型号（不作标识字段发送）、账号与身份信息
  （不登录、不携带认证信息）、精确位置（主动层不取位置，APPROXIMATELY_LOCATION
  的用途不变）。

### 7.2 数据最小化（只存结论，不存载荷）

- 存：设备存活与否、开放端口类别、协议分类结果（RTSP / ONVIF / HTTP 类别）、
  厂商分类、证据分项（复用被动层四类证据 + 主动证据类别）、审计记录。
- 不存：报文载荷、Server 横幅原文、流地址、完整设备描述文档、截图、密码、
  任何认证信息、精确位置。
- 审计记录字段限定：时间、任务、能力、目标范围、结果数、成功 / 失败、ACL 表版本；
  只存本地，可查、可删；卸载即随应用数据清除。

### 7.3 身份最小化

- 探测报文不带设备名、账号、App 标识；HTTP 探测的标识头用通用值或空，
  不写 App 名与版本号。
- 不登录任何目标；不携带任何认证信息；不利用任何漏洞。

### 7.4 可见性与可控性

- 设置页“主动扫描授权”专页：ACL 表（每项能力说明 + 开关）+ 审计日志
  （可查、可删）+ 一键关闭全部主动能力；关闭后安防页主动入口隐藏，
  被动扫描不受影响。
- 每次扫描前弹窗（四要素）；扫描中可随时取消；取消即关全部 socket。
- 系统权限关系须在文案中说明：INTERNET 是系统授予、系统不会再弹窗，
  App 内的这次询问就是全部告知——用户要理解“同意”发生在 App 内，不是系统弹窗。

### 7.5 他人网络场景与法律边界

- 在酒店 / 租房等非自有网络扫描前，弹窗追加提示：你正在他人网络上扫描；
  仅扫描本网段、只读探测、不改配置、不登录；请遵守当地法律。
- 法律边界（硬性）：只读探测；不绕过认证；不利用漏洞；不造成目标拒绝服务
  （速率与并发上限即为此设）。

## 8. API 能力核查（精简版，只保留实现必需的结论）

| 能力 | 鸿蒙 API | 状态 | 说明 |
|---|---|---|---|
| TCP 连接探测 | `socket.constructTCPSocketInstance()` → `connect()` / `close()` | ✅ 可用 | 需 INTERNET；可设超时；是网段存活探测的正途 |
| UDP 发送 / 接收 | `socket.constructUDPSocketInstance()` → `send()` / `on('message')` | ✅ 可用 | 需 INTERNET；向组播地址发送 Probe 不需要先加组；单播回包可正常接收 |
| UDP 组播成员（收组播宣告） | 原生 `@ohos.net.socket` 的 `addMembership` 存在性 | ⚠️ 待实测 | P3-3 阶段桌面端核对 SDK 声明称 UDPSocket 确有 `addMembership / dropMembership`（@since 11）；但仓内无 SDK 声明文件可复核，ACL 引擎落地前须以真机验证为准；验证失败则组播监听不可用，A6 只做主动查询 |
| 原始套接字 / ARP 发包 | 无公开 API | ❌ 没有 | App 无法自己发 ARP 请求 |
| ARP 表 / 对端 MAC 读取 | 无公开 API | ❌ 没有 | **硬约束：局域网设备的 MAC 与厂商 OUI 无法直接获取**；厂商识别改走服务横幅 / 主机名 / SSDP 设备描述类型字段；不承诺 OUI 判定 |
| 本机 IP | `wifiManager.getIpInfo()` | ✅ 可用 | 需 GET_WIFI_INFO（已声明） |
| 网段前缀长 | `connection.getConnectionProperties()` → `linkAddresses`（含前缀长） | ⚠️ 待核对 | 需 GET_NETWORK_INFO（未声明）；如字段或权限不符，按第 5 节降级方案处理 |
| 后台长连接 | `KEEP_BACKGROUND_RUNNING`（已声明） | ⛔ 不用 | 主动扫描限定在前台任务内执行，扫描结束即关全部 socket；不走后台常驻，不留后台探测 |

- **INTERNET 已用于两处固定源 HTTPS**：特征库更新（`FieldwatchCatalogRepository` 经
  `ngfNetworkClient`）与反馈中心（`FieldwatchFeedbackService` 经 `http.createHttp`，
  固定源 `feedback.manxia.top`）。主动探测与这两处**同权限、不同风险**，
  必须分流：固定源请求走现有网络客户端，主动探测只走 ACL 引擎，ACL 引擎之外
  任何代码路径不得创建指向内网地址的 socket。
- **无 Socket 调用**：全仓 grep 只有注释命中，主动层是全新模块，无历史包袱。
  附带清理项：`FieldwatchSecurityPassive` 头部注释仍写主动探测“未获用户批准”，
  与决策修订已矛盾，ACL 引擎落地时顺手改掉，改成指向本文。
- **WifiLink 只有 SSID + 随机 BSSID**：无 IP / 网段字段；主动层需新增网络信息获取，
  不得复用 BSSID 做长期锚（`bssidStable` 恒为 false 的结论不变）。
- **既有授权模式**：`FieldwatchPermissions`（权限规格 + `checkAccessTokenSync` /
  `requestPermissionsFromUser`，运行时规格表目前只列蓝牙、星闪、近似位置 3 项）
  与 4 步首启引导。主动 ACL 复用“先说明、后请求、可撤销”的模式，但有一条硬性区别：
  **首启不预授权主动能力**。主动授权只在任务触发时、针对本次扫描会话产生，
  不得并入首启一次性打包授权——否则“按任务通报”就落空了。
- **既有底线不变**：数据只在本机；特征库更新与反馈走固定源 HTTPS；
  主动扫描结果同样只存本机，绝不随反馈或任何通道上传。
