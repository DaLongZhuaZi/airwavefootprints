# 主动扫描授权与隐私体系设计（App 内 ACL）

> 决策变更（2026-10-27 晚，用户修订）：局域网主动探测从“暂不做”改为**在严格授权与隐私体系下做**。
> 《日常功能实测反馈四项完善方案.md》3.2 与附录 A.2 / B 的“暂不做”以本文为准更新：
> 不是无条件重启主动层，而是只有本文的 ACL 引擎、任务绑定、范围硬约束、隐私体系全部落地后，
> 主动能力才允许进入安防扫描任务；任一环节缺失，主动入口保持关闭。
> 本文档是设计稿，不是实现；实现前先跑第 6 节阶段一的真机验证清单，验证结论写入实施汇报。

## 1. 鸿蒙机制核查：系统 ACL 是什么，本 App 用得上哪一段

### 1.1 系统 ACL（查文档所得）

HarmonyOS Next 的 ACL（Access Control List）是“特殊通行证”机制：

- 应用分三级 APL：normal / system_basic / system_core，级别越高可申请的权限越深。
  普通第三方应用是 normal APL，只能申请 normal 级权限，不能直接拿 system_basic / system_core 级权限。
- normal APL 应用因业务需要 system_basic 级权限时，走 ACL 流程：
  开发者向应用市场（AGC）提交申请材料（申请理由、使用场景描述、功能实现方式等）
  → AGC 严格审核 → 通过后获得相应权限证书 → 工程内按规定流程声明配置
  → 运行时应用通过 ACL 机制向系统请求，系统再次核验应用合法性与权限使用场景
  → 全部合规才授予**临时**高级权限。
- 来源为 2024-11（API 12 时代）的机制说明，实施前须以现行 AGC 文档复核流程细节；
  本文档只依赖“ACL = 审批 + 证书 + 运行时复核 + 临时授权”这一机制定义，不依赖其具体表单字段。

### 1.2 关键结论：主动扫描本身不需要系统 ACL，系统 ACL 也管不住它

- 主动扫描的发包能力走 `@ohos.net.socket`（TCP / UDP），所需权限是
  `ohos.permission.INTERNET`，属于 system_grant（系统授予，安装时自动给，不弹窗、不问用户）。
- 也就是说：**系统层面，“向谁发包、发什么、发多少”没有任何关卡**。
  同一个 INTERNET 权限，既可以向固定源服务器拉特征库，也可以向内网任意主机发探测包，
  系统不区分这两类行为。
- 因此“严格根据功能 / 任务去通报主动扫描的使用”**只能由 App 内 ACL 实现**，
  系统 ACL 不能替代它。系统 ACL 只有在 App 需要更高级别权限时才登场，
  本 App 有一个现成的例子：`GET_WIFI_PEERS_MAC`。
  没有该权限时系统给的 BSSID 是随机值——WifiLink 已核实（`bssidStable` 恒为 false，
  Wi-Fi 目标只能靠 SSID + 当前连接关系 + RSSI 行为识别）。如未来需要真实 BSSID，
  才需要走 AGC 的 ACL 申请流程；主动扫描本身不需要。

### 1.3 权限分级对照（本 App 相关）

| 权限 | 授予方式 | 本 App 现状 | 与主动层的关系 |
|---|---|---|---|
| `ohos.permission.INTERNET` | system_grant，安装自动给 | 已声明，无 reason（系统授予不需要） | 主动发包的唯一系统权限；不区分目标，必须由 App 内 ACL 约束 |
| `ohos.permission.GET_WIFI_INFO` | user_grant，需 reason + usedScene | 已声明（WiFi 扫描） | 被动 WiFi 扫描的基础；主动层复用，不新增 |
| `ohos.permission.APPROXIMATELY_LOCATION` | user_grant | 已声明（近似位置，无精确 LOCATION） | WiFi 扫描的配套；主动层不因此获得精确位置 |
| `ohos.permission.GET_NETWORK_INFO` | 待核对（见第 7 节） | **未声明** | 网段前缀获取可能需要；如需则补声明并进权限规格表 |
| `ohos.permission.GET_WIFI_PEERS_MAC` | 受限权限，疑似需 ACL / 严格审批 | **未声明** | 真实 BSSID 与对端 MAC 的唯一正途；不申请则接受“无 MAC”约束（见 2 节） |

## 2. API 能力核查表（查文档 + 核对实现）

| 能力 | 鸿蒙 API | 状态 | 说明 |
|---|---|---|---|
| TCP 连接探测 | `socket.constructTCPSocketInstance()` → `connect()` / `close()`，`on('connect'/'close'/'error')` | ✅ 可用 | 需 INTERNET；可设超时；是网段存活探测的正途 |
| UDP 发送 / 接收 | `socket.constructUDPSocketInstance()` → `send()` / `on('message')` | ✅ 可用 | 需 INTERNET；向组播地址发送 Probe 不需要先加组；单播回包可正常接收 |
| UDP 组播成员（收组播宣告） | 原生 `@ohos.net.socket` 未见 `addMembership` / `setBroadcast` | ⚠️ 待实测 | 第三方 RN 封装有这两个方法，不等于原生 API 有；SSDP NOTIFY / mDNS 宣告的被动监听能力以真机验证为准；验证失败则 SSDP / mDNS 只做主动查询（M-SEARCH 发出去、等单播回包），不做组播监听 |
| 原始套接字 / ARP 发包 | 无公开 API | ❌ 没有 | App 无法自己发 ARP 请求 |
| ARP 表 / 对端 MAC 读取 | 无公开 API | ❌ 没有 | **硬约束：局域网设备的 MAC 与厂商 OUI 无法直接获取**；厂商识别改走服务横幅 / 主机名 / SSDP 设备描述类型字段；不承诺 OUI 判定 |
| 本机 IP | `wifiManager.getIpInfo()` | ✅ 可用 | 需 GET_WIFI_INFO（已声明） |
| 网段前缀长 | `connection.getConnectionProperties()` → `linkAddresses`（含前缀长） | ⚠️ 待核对 | 需 GET_NETWORK_INFO（未声明）；如字段或权限不符，网段推导降级为“本机 IP + /24 假设”并在 UI 明示假设，或拒绝执行（见 4.4） |
| 后台长连接 | `KEEP_BACKGROUND_RUNNING`（已声明） | ⛔ 不用 | 主动扫描限定在前台任务内执行，扫描结束即关全部 socket；不走后台常驻，不留后台探测 |

## 3. 当前实现核对（main `ca064ee`，以代码为准）

- **权限**：`module.json5` 共声明 14 项（INTERNET、ACCESS_NEARLINK、ACCESS_BLUETOOTH、
  GET_WIFI_INFO、SET_WIFI_INFO、DETECT_GESTURE、ACTIVITY_MOTION、KEEP_BACKGROUND_RUNNING、
  PUBLISH_AGENT_REMINDER、ACCESS_BIOMETRIC、ACCELEROMETER、GYROSCOPE、VIBRATE、
  APPROXIMATELY_LOCATION）。此前审计摘要写“13 项”是计数错误，以本次精确计数为准。
- **INTERNET 已用于两处固定源 HTTPS**：特征库更新（`FieldwatchCatalogRepository` 经
  `ngfNetworkClient`）与反馈中心（`FieldwatchFeedbackService` 经 `http.createHttp`，
  固定源 `feedback.manxia.top`）。主动探测与这两处**同权限、不同风险**，
  必须分流：固定源请求走现有网络客户端，主动探测只走 ACL 引擎，ACL 引擎之外
  任何代码路径不得创建指向内网地址的 socket。
- **无 Socket 调用**：全仓 grep `TCPSocket / UDPSocket / net.socket / addMembership / ARP`
  只有无关命中（线性功率函数、雷达聚类、注释），主动层是全新模块，无历史包袱。
- **WifiLink 只有 SSID + 随机 BSSID**：无 IP / 网段字段；主动层需新增网络信息获取，
  不得复用 BSSID 做长期锚（`bssidStable` 恒为 false 的结论不变）。
- **既有授权模式**：`FieldwatchPermissions`（权限规格 + `checkAccessTokenSync` /
  `requestPermissionsFromUser`，运行时规格表目前只列蓝牙、星闪、近似位置 3 项）
  与 4 步首启引导（`FieldwatchOnboardingPage` + `FieldwatchOnboardingGuard`）。
  主动 ACL 复用“先说明、后请求、可撤销”的模式，但有一条硬性区别：
  **首启不预授权主动能力**。主动授权只在任务触发时、针对本次扫描会话产生，
  不得并入首启一次性打包授权——否则“按任务通报”就落空了。
- **既有底线不变**：数据只在本机；特征库更新与反馈走固定源 HTTPS；
  主动扫描结果同样只存本机，绝不随反馈或任何通道上传。

## 4. App 内 ACL 设计

### 4.1 ACL 表模型

ACL 表是本地数据（可查看、可导出审计、可一键关闭），每条记录：

| 字段 | 含义 |
|---|---|
| 能力 id | A1–A7（见 4.2） |
| 任务 / 功能 | 哪个任务可用（安防扫描 / WiFi 体检 / 找东西，见 4.3） |
| 目标范围 | 允许的目标集合（当前已连 WiFi 网段内主机；排除项见 4.4） |
| 数据处理 | 该能力允许记录什么、不允许记录什么（见 5.2） |
| 速率 / 并发 / 超时 | 单目标超时、并发上限、总时长上限、重试策略（不重试） |
| 授权粒度 | 仅本次扫描会话；会话结束即失效；设置页可手动重开 |
| 告知文案 key | 弹窗四要素（能力、范围、暴露面、数据去向）的文案键 |
| 审计字段 | 每次执行记：时间、任务、能力、目标范围、结果数、成功 / 失败 |

ACL 引擎是唯一放行点：任务代码不直接创建 socket，一律向 ACL 引擎申请
（任务 + 能力 + 目标），引擎核对“任务绑定 + 本次会话授权 + 目标范围”三项，
任一项不符直接拒绝并记审计，拒绝本身也是一条可查记录。

### 4.2 能力全表（完整覆盖全部主动方法）

| 能力 | 对应主动方法 | 允许的操作 | 明确不做的事 |
|---|---|---|---|
| A1 网段存活探测 | ARP 扫网段的**替代实现**（ARP 无 API，见 2 节） | 对网段内主机做 TCP connect（常见端口）与 UDP 探测，判定存活 | 不发 ARP；不拿 MAC；不对存活主机做任何超出 A2 的事 |
| A2 端口探针 | 端口探针 | 白名单端口表：80、443、554、8000、8080、8443、8899、1935、3702、37777、34567、9000、1900、5353；只记 open / closed | 不读横幅全文；不扫白名单外端口；不扫公网 |
| A3 RTSP 探测 | RTSP OPTIONS / DESCRIBE | 只取 Server 标识类别与 SDP 编码类型，用于厂商分类 | 不存流地址；不拉流；不试口令 |
| A4 ONVIF 探测 | WS-Discovery Probe + GetServices / GetCapabilities | 组播 Probe（`239.255.255.250:3702`，NetworkVideoTransmitter）+ 单播回包；仅取设备类型与服务清单 | 不调 GetStreamUri；不拉流；不调需认证的配置接口 |
| A5 HTTP 横幅 | HTTP 横幅 / 管理页特征 | 只取 Server 头类别，用于厂商分类 | 不爬管理页；不试默认口令；不登录 |
| A6 服务发现查询 | mDNS / SSDP 主动查询（M-SEARCH） | 仅服务类型与设备描述类型字段（如 UPnP `DigitalSecurityCamera:1` 方向） | 不做组播监听（除非阶段一验证通过）；不存完整设备描述文档 |
| A7 厂商二进制魔数 | 大华 37777、Reolink 9000 Baichuan、XMEye 34567 等私有协议握手字节比对 | 只比对魔数字节，命中即厂商分类 | 不发后续载荷；不进入会话；不利用协议漏洞 |

**排除项（ACL 表之外，任何任务不得申请）**：弱口令 / 默认口令尝试、RTSP 拉流、
ONVIF GetStreamUri 拉流、漏洞利用、配置修改、登录尝试、公网目标、历史网络、
后台常驻扫描、目标拒连后的重试爆破。

### 4.3 任务绑定（最小化：哪个任务能用什么）

| 任务 | 可用能力 | 理由 |
|---|---|---|
| 安防扫描 | A1–A7 全部 | 任务本身就是“找出可疑联网设备”，需要完整枚举 + 协议分类 |
| WiFi 体检 | 仅 A1 | 体检只需要“当前网络里有哪些存活主机、与当前 AP 的关系”，不需要摄像头协议分类；端口与协议能力不对体检开放 |
| 找东西 | 无 | 找东西是认领已发现的蓝牙 / WiFi 设备，保持纯被动；主动探测对其无收益，只增风险 |
| 日常页 / 图鉴 / 记录 / 设置 | 无 | 非任务页不触发任何主动能力 |

### 4.4 目标范围硬约束（代码级，不是文案）

- 仅当前已连 WiFi 的网段：由 `linkAddresses` 前缀长推导；推导失败时，
  降级方案（二选一，实施时定死并写进汇报）：（a）按本机 IP + /24 假设并在 UI 明示假设；
  （b）拒绝执行并提示“无法确定网段”。不得静默按猜测的网段扫描。
- 排除本机地址与网关地址（网关是路由器，探测它无分类收益且更敏感）。
- 排除公网地址、排除历史 SSID 网络、排除蜂窝网络（仅 WiFi 下可用）。
- 并发上限、单目标超时、总时长上限在实施时定死（建议起点：并发 16、单目标 800ms、
  总时长 60s，实测后调）；目标拒连 / 超时不重试；扫描中用户取消即关全部 socket。

### 4.5 授权流程（任务级通报）

1. 用户在安防扫描页点“开始主动扫描”（被动扫描与主动扫描是两个分开的入口与按钮，
   不得把主动能力藏进被动扫描的默认流程）。
2. 弹窗通报四要素，缺一不可：**本次将用的能力**（A1–A7 逐项列出，非笼统的“网络扫描”）、
   **目标范围**（当前 WiFi 的 SSID + 网段）、**会暴露什么**（见 5.1）、**数据去向**
   （只存本机、不上传、可删除）。
3. 用户确认后授权仅对本次扫描会话有效；会话结束（完成 / 取消 / 切后台 / 断网）
   即失效，下次重新通报。
4. 拒绝时零发包：弹窗拒绝后不得有任何 socket 创建（验收时以日志抽查为准）；
   拒绝只针对本次，入口保留；设置页提供“关闭该能力”——关闭后需手动重开，
   避免一次误点永久失去功能，也避免反复弹窗骚扰。
5. 审计：每次扫描（包括被拒绝的申请）记一条本地审计记录，设置页可查、可删。

## 5. 隐私处理与防自身信息暴露体系

### 5.1 暴露面清单（向用户诚实列出，弹窗文案照此写）

- 本机 IP 会出现在目标设备 / 路由器的日志里——主动扫描无法做到“不留痕”，
  这是与被动扫描的本质区别，弹窗必须明说。
- 探测报文特征（端口序列、ONVIF Probe、M-SEARCH）可被识别为扫描行为；
  同网段监听者能看到组播 Probe。
- 扫描结果若上传，会暴露用户所在网络与家庭设备清单——因此结果绝不上传（5.2）。
- 以下**不会**暴露：本机设备名 / 型号（不作标识字段发送）、账号与身份信息
  （不登录、不携带认证信息）、精确位置（主动层不取位置，APPROXIMATELY_LOCATION
  的用途不变）。

### 5.2 数据最小化（只存结论，不存载荷）

- 存：设备存活与否、开放端口类别、协议分类结果（RTSP / ONVIF / HTTP 类别）、
  厂商分类、证据分项（复用被动层四类证据 + 主动证据类别）、审计记录。
- 不存：报文载荷、Server 横幅原文、流地址、完整设备描述文档、截图、密码、
  任何认证信息、精确位置。
- 审计记录字段限定：时间、任务、能力、目标范围、结果数、成功 / 失败；
  只存本地，可查、可删；卸载即随应用数据清除。

### 5.3 身份最小化

- 探测报文不带设备名、账号、App 标识；HTTP 探测的标识头用通用值或空，
  不写 App 名与版本号。
- 不登录任何目标；不携带任何认证信息；不利用任何漏洞。

### 5.4 可见性与可控性

- 设置页“主动扫描授权”专页：ACL 表（每项能力说明 + 开关）+ 审计日志
  （可查、可删）+ 一键关闭全部主动能力；关闭后安防页主动入口隐藏，
  被动扫描不受影响。
- 每次扫描前弹窗（四要素）；扫描中可随时取消；取消即关全部 socket。
- 系统权限关系须在文案中说明：INTERNET 是系统授予、系统不会再弹窗，
  App 内的这次询问就是全部告知——用户要理解“同意”发生在 App 内，不是系统弹窗。

### 5.5 他人网络场景与法律边界

- 在酒店 / 租房等非自有网络扫描前，弹窗追加提示：你正在他人网络上扫描；
  仅扫描本网段、只读探测、不改配置、不登录；请遵守当地法律。
- 法律边界（硬性）：只读探测；不绕过认证；不利用漏洞；不造成目标拒绝服务
  （速率与并发上限即为此设）。

## 6. 实施路线（给桌面端的大纲，不含代码细节）

- **阶段一（能力验证，先行）**：真机验证清单——UDPSocket 组播发送与接收、
  `linkAddresses` 前缀长与 GET_NETWORK_INFO 需求、`getIpInfo` 字段、
  TCP connect 超时与并发表现、前台 / 切后台 socket 存活、部分 AP 对组播 Probe
  的转发行为。输出验证报告；任一关键项失败，对应能力降级并标注，不得硬上。
- **阶段二（ACL 引擎 + 安防任务接线）**：ACL 表、授权弹窗、审计、范围硬约束、
  速率 / 超时；先接 A1 + A2 + A6（枚举与发现），再接 A3–A5、A7（协议握手）；
  每批 hvigor test + 真机回归。
- **阶段三（隐私专页 + 回归）**：设置页 ACL 专页、审计查看 / 删除、一键关闭；
  全量回归（被动层不受影响、版本保持 1.1.0）；提交推送 main，并在文档末尾补录实施现状。
- **验收标准**：逐项对照 ACL 表；拒绝授权时零发包；超范围目标零发包；
  审计记录与实际发包抽查一致；被动扫描行为与结论不受影响。

## 7. 待核对清单（实施前或阶段一必须闭合）
