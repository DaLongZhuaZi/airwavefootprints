## 1. P1 归一化与匹配上下文缓存

### 改动

| 文件 | 改动 |
|---|---|
| `domain/signatures/FieldwatchSignatureModels.ets` | 重写 `signatureHexOnly()`：ASCII 查表（`HEX_UPPER_CODES`）+ 数组 `join`；新增「已是规范大写十六进制 → 原样返回」的**零分配快路径** |
| `domain/signatures/FieldwatchSignatureEngine.ets` | `SignatureMatchContext` 增加归一化缓存：`addressHex()`、`oui()`、`nameLower()`、`manufacturerDataHexNormalized()`、`serviceUuidAliasesAt(i)`、`serviceDataHexAt(i)`、`serviceDataAliasesAt(i)`、`vendorIeHexAt(i)`；`uuidHits()` 改为接收**已归一化别名数组**；`SignatureManufacturerDataRule` / `SignatureContainsRule` / `CompiledSignatureIndex.ouiHits` / `serviceDataHits` / `vendorIeHitsOui` / `isAppleContinuity` / `isTeslaPhoneKeyIBeacon` / `hasFindMyAccessoryUuid` / `suggestFleet` 全部改读缓存；`matchesPrefix()` 改收 context |

### 关键点

- 原来 `result += raw.charAt(i).toUpperCase()`：n 字符 ≈ 3n 次临时字符串分配 + O(n²) 拷贝。
- 更要命的是**观测侧归一化没有缓存**：规则侧早在 `compile()` 里预编译好了，但 `hits()` 内部按「规则数 × 字段数」把同一份 context 重算了一遍。现在收敛为「每字段一次」。
- `uuidHits` 之前把**已归一化的字符串**又塞回 `signatureUuidAliases()` 重算，属于纯粹的重复劳动。

## 2. P2 匹配结果缓存与写入合并

### 改动

| 文件 | 改动 |
|---|---|
| `domain/signatures/FieldwatchSignatureEngine.ets` | 新增 `SignatureMatchContext.matchFingerprint()`：只拼接参与判定的字段（kind / 归一化地址 / 名称 / hiddenSsid / 厂商 id / 归一化厂商数据 / serviceUuids / serviceData(uuid+data) / 归一化厂商 IE） |
| `application/FieldwatchApplication.ets` | 新增 `SignatureMatchCacheEntry` 与 `resolveSignatureMatch()`：**同设备 + 同指纹直接复用命中列表与解码字段**；`ingestNow()` 改走缓存；特征库整体替换（引用变化）自动失效，`saveUserFleet()` 就地编辑时显式失效；内存日志修剪从「每条一次 `splice`」改为「攒够 128 条修剪一次」（`LOG_TRIM_SLACK`）；新增 `MATCH_CACHE_LIMIT = 2048` |
| `data/FieldwatchObservationRepository.ets` | `append()` 改为**内存排队 + 单条多行 INSERT**：攒够 24 条或等 400ms 落库（`BATCH_ROWS` / `FLUSH_DELAY_MS`），不再每条一次事务提交；`prune()` 改为每累计 100 行一次；`flush()` 先取消定时器再落库 |

### 为什么用多行 INSERT 而不是显式事务

`ngfRdbManager` 是共享单例，`FieldwatchOwnDeviceRepository` 也会写同一个 store。开显式事务后，其他写入会被卷进我们的未提交事务里（回滚时会一起丢）。单条多行 INSERT 天然原子、互不干扰，且同样把「每次观测一次提交」变成「每批一次提交」。24 行 × 12 列 = 288 个绑定参数，远低于 SQLite 的 999 上限。

### 行为不变性

指纹语义是「同指纹 ⇒ 匹配结果必然相同」，因此复用不改变匹配结果；命中列表数组不做任何就地修改（已核对全仓 `signatureIds` 只有整体赋值），共享安全。

## 3. P3 列表构建去重计算

### 改动

| 文件 | 改动 |
|---|---|
| `ui/FieldwatchUiState.ets` | 新增 `SignatureFleetIndex`（静态索引，按「数组引用 + 长度」失效）与导出函数 `fleetById()`；`matchedSignatureNames()`、`signatureColorIndex()`、`signatureHitCounts()` 全部改走索引 |
| `pages/fieldwatch/FieldwatchPage.ets` | `categoryFor()` / `signatureText()` 改走 `fleetById()`；`classCount()` 改为**一次遍历产出全部类别计数**（原来每个类别扫一遍全表，20 个类别 = 20 次全表）；`classFleetCount()` 按目录数组记忆化（原来每个类别行 filter 一遍 600+ 条目录）；`signatureReasonText()` 按「设备 + 命中集合 + 目录规模」记忆化（原来每次详情重建都跑一遍 `explain()`，那是 O(目录 × 规则)） |

### 为什么这些代价高

这些方法都在 `@Builder` 行构建里被调用，而 ArkUI 每个状态变化都会重跑 build。目录有 600+ 条签名时，一次 `find` 就是 600 次比较，乘上「每帧 × 每行」正是录制里 `anonymous`（11.0%）+ `categoryFor`（2.8%）+ `__getResourceId__`（3.8%）的来源。

## 4. P4 雷达几何脏检查

### 改动

| 文件 | 改动 |
|---|---|
| `pages/fieldwatch/FieldwatchPage.ets` | ① `refresh()` 里的几何重建改为**只在「雷达模式且页面可见」时执行**（列表/类别/轨迹/时间线模式不绘制雷达）；② `rebuildRadarGeometry(force = false)` 增加**输入指纹脏检查**（点数 + 缩放 + 每个点的量化 RSSI + key 长度），未变化直接返回，手势结束用 `force=true` 强制重算；③ 删除 `refresh()` 里**重复构建** `clusteredKeys` 大字符串的那段（几千台设备约 250 KB，每秒钟白拼一次） |
| `ui/FieldwatchRadarCluster.ets` | `relaxNodes` 迭代 28 轮 → 18 轮（收敛主要发生在前 10 轮） |

RSSI 量化到 5 dBm 一档是刻意的：抖动范围内的位移只有 1~2 px，肉眼不可辨，但能让脏检查真正命中。

## 5. P5 匹配下放任务池 —— 不落地，仅保留方案

录制里的 JS 采样 **约 95% 落在主线程**，说明匹配、解码、列表构建、几何重建全在 UI 线程上跑。理论上可把 `matchContext()` + `decodeFields()` 下发 `taskpool`，但需要解决：

1. `SignatureFleet[]`（含 `rules` / `decode` 嵌套结构）跨线程序列化，单次传输成本可能超过匹配本身；
2. 回主线程还要把结果写回 `sighting.signatureIds`，状态派发仍在主线程；
3. ArkTS 的 `@Sendable` 约束会牵动 `FieldwatchSignatureModels` 的整条类型链。

**结论**：P1–P4 已把匹配本身的开销砍掉大部分（尤其是「同指纹直接复用」相当于在应用层做了一次去重），任务池的边际收益不抵复杂度与回归风险。若后续复测主线程仍 >45%，再按「只传最小快照」的方案落地。

### 8.2 温度与功耗

| 指标 | 基线 | Energy2 | 说明 |
|---|---|---|---|
| 起始 shell 温度 | 42.01℃ | 44.30℃ | 新构建是**浸泡态**起点，高了 2.3℃ |
| 51s 内温升 | **+0.84℃** | **+0.22℃** | |
| 温升斜率 | **+0.99℃/min** | **+0.26℃/min** | **−74%** |
| thermal_level | 3 | 4 | 系统温控档位更高（更热） |
| 电池电流均值 | −1496 mA | −1577 mA | 基本持平（+5%） |

**怎么读这组数**：

1. 温升斜率降了 74% —— 同样的 51 秒窗口里，设备从"快速升温"变成"接近热平衡"。
2. 绝对温度反而高 2.3℃，**不是新构建更热**，而是这次录制起点就带着前 7 分钟的积热，且系统已经进了更高的温控档（level 4 会主动降频）。要比较绝对温度必须用「同一台机、同一冷启动条件」的两条录制。
3. 电池电流基本持平、GPU 能耗上升 —— 省下来的 CPU 被"真的在画 3.5 倍帧"的 GPU/合成器消耗掉了。**发热分布从「4 条 GC 线程 + 主线程打满」变成「按 vsync 节奏出帧」**，瞬时功耗尖峰消失，这才是温升斜率大幅下降的原因。

### 8.4 结论

- P1–P4 的核心目标全部达成：主线程从"几乎 100% 打满"降到 35.7%，GC 从 39.5% 降到 3.2%，帧率从 16.7fps 提到 58.4fps 且帧间隔 p90 = 18.3ms。
- 温升斜率 −74%，但**绝对温度受浸泡态与温控档位影响，本轮无法给出"最终稳态温度"结论**；需要一次冷启动对照录制才能定论。
- P5（匹配下放任务池）的收益已进一步降低：匹配相关采样合计不足 5%，不值得为此引入跨线程序列化复杂度。

### 8.5 下一轮可选方向（若还要继续压）

1. `drawRadar`（20.2%）：Canvas 每帧重绘整套雷达背景。可把静态底板（圈层、刻度、网格）缓存成一张离屏图，每帧只画扫描线 + 图标，预计能砍掉一半绘制成本。
2. `__getResourceId__`（10.8%）：行构建里大量 `$r()`。可在 `aboutToAppear` 里把这些资源解析成字符串存字段，builder 里直接用。
3. `anonymous`（18.7%）：List 行 builder。可考虑把高频变化字段（RSSI、时间）拆成独立小节组件，减少整行重建范围。
