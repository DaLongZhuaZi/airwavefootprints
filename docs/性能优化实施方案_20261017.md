## 1. P1 归一化与匹配上下文缓存

### 改动

| 文件 | 改动 |
|---|---|
| `domain/signatures/FieldwatchSignatureModels.ets` | 重写 `signatureHexOnly()`：ASCII 查表（`HEX_UPPER_CODES`）+ 数组 `join`；新增「已是规范大写十六进制 → 原样返回」的**零分配快路径** |
| `domain/signatures/FieldwatchSignatureEngine.ets` | `SignatureMatchContext` 增加归一化缓存：`addressHex()`、`oui()`、`nameLower()`、`manufacturerDataHexNormalized()`、`serviceUuidAliasesAt(i)`、`serviceDataHexAt(i)`、`serviceDataAliasesAt(i)`、`vendorIeHexAt(i)`；`uuidHits()` 改为接收**已归一化别名数组**；`SignatureManufacturerDataRule` / `SignatureContainsRule` / `CompiledSignatureIndex.ouiHits` / `serviceDataHits` / `vendorIeHitsOui` / `isAppleContinuity` / `isTeslaPhoneKeyIBeacon` / `hasFindMyAccessoryUuid` / `suggestFleet` 全部改读缓存；`matchesPrefix()` 改收 context |

### 关键点

- 原来 `result += raw.charAt(i).toUpperCase()`：n 字符 ≈ 3n 次临时字符串分配 + O(n²) 拷贝。
- 更要命的是**观测侧归一化没有缓存**：规则侧早在 `compile()` 里预编译好了，但 `hits()` 内部按「规则数 × 字段数」把同一份 context 重算了一遍。现在收敛为「每字段一次」。
- `uuidHits` 之前把**已归一化的字符串**又塞回 `signatureUuidAliases()` 重算，属于纯粹的重复劳动。

## 2. P2 匹配结果缓存与写入合并

### 改动

| 文件 | 改动 |
|---|---|
| `domain/signatures/FieldwatchSignatureEngine.ets` | 新增 `SignatureMatchContext.matchFingerprint()`：只拼接参与判定的字段（kind / 归一化地址 / 名称 / hiddenSsid / 厂商 id / 归一化厂商数据 / serviceUuids / serviceData(uuid+data) / 归一化厂商 IE） |
| `application/FieldwatchApplication.ets` | 新增 `SignatureMatchCacheEntry` 与 `resolveSignatureMatch()`：**同设备 + 同指纹直接复用命中列表与解码字段**；`ingestNow()` 改走缓存；特征库整体替换（引用变化）自动失效，`saveUserFleet()` 就地编辑时显式失效；内存日志修剪从「每条一次 `splice`」改为「攒够 128 条修剪一次」（`LOG_TRIM_SLACK`）；新增 `MATCH_CACHE_LIMIT = 2048` |
| `data/FieldwatchObservationRepository.ets` | `append()` 改为**内存排队 + 单条多行 INSERT**：攒够 24 条或等 400ms 落库（`BATCH_ROWS` / `FLUSH_DELAY_MS`），不再每条一次事务提交；`prune()` 改为每累计 100 行一次；`flush()` 先取消定时器再落库 |

### 为什么用多行 INSERT 而不是显式事务

`ngfRdbManager` 是共享单例，`FieldwatchOwnDeviceRepository` 也会写同一个 store。开显式事务后，其他写入会被卷进我们的未提交事务里（回滚时会一起丢）。单条多行 INSERT 天然原子、互不干扰，且同样把「每次观测一次提交」变成「每批一次提交」。24 行 × 12 列 = 288 个绑定参数，远低于 SQLite 的 999 上限。

### 行为不变性

指纹语义是「同指纹 ⇒ 匹配结果必然相同」，因此复用不改变匹配结果；命中列表数组不做任何就地修改（已核对全仓 `signatureIds` 只有整体赋值），共享安全。

## 3. P3 列表构建去重计算

### 改动

| 文件 | 改动 |
|---|---|
| `ui/FieldwatchUiState.ets` | 新增 `SignatureFleetIndex`（静态索引，按「数组引用 + 长度」失效）与导出函数 `fleetById()`；`matchedSignatureNames()`、`signatureColorIndex()`、`signatureHitCounts()` 全部改走索引 |
| `pages/fieldwatch/FieldwatchPage.ets` | `categoryFor()` / `signatureText()` 改走 `fleetById()`；`classCount()` 改为**一次遍历产出全部类别计数**（原来每个类别扫一遍全表，20 个类别 = 20 次全表）；`classFleetCount()` 按目录数组记忆化（原来每个类别行 filter 一遍 600+ 条目录）；`signatureReasonText()` 按「设备 + 命中集合 + 目录规模」记忆化（原来每次详情重建都跑一遍 `explain()`，那是 O(目录 × 规则)） |

### 为什么这些代价高

这些方法都在 `@Builder` 行构建里被调用，而 ArkUI 每个状态变化都会重跑 build。目录有 600+ 条签名时，一次 `find` 就是 600 次比较，乘上「每帧 × 每行」正是录制里 `anonymous`（11.0%）+ `categoryFor`（2.8%）+ `__getResourceId__`（3.8%）的来源。

## 5. P5 匹配下放任务池 —— 不落地，仅保留方案

录制里的 JS 采样 **约 95% 落在主线程**，说明匹配、解码、列表构建、几何重建全在 UI 线程上跑。理论上可把 `matchContext()` + `decodeFields()` 下发 `taskpool`，但需要解决：

1. `SignatureFleet[]`（含 `rules` / `decode` 嵌套结构）跨线程序列化，单次传输成本可能超过匹配本身；
2. 回主线程还要把结果写回 `sighting.signatureIds`，状态派发仍在主线程；
3. ArkTS 的 `@Sendable` 约束会牵动 `FieldwatchSignatureModels` 的整条类型链。

**结论**：P1–P4 已把匹配本身的开销砍掉大部分（尤其是「同指纹直接复用」相当于在应用层做了一次去重），任务池的边际收益不抵复杂度与回归风险。若后续复测主线程仍 >45%，再按「只传最小快照」的方案落地。

### 8.4 结论

- P1–P4 的核心目标全部达成：主线程从"几乎 100% 打满"降到 35.7%，GC 从 39.5% 降到 3.2%，帧率从 16.7fps 提到 58.4fps 且帧间隔 p90 = 18.3ms。

- P5（匹配下放任务池）的收益已进一步降低：匹配相关采样合计不足 5%，不值得为此引入跨线程序列化复杂度。

### 8.5 下一轮可选方向（若还要继续压）

1. `drawRadar`（20.2%）：Canvas 每帧重绘整套雷达背景。可把静态底板（圈层、刻度、网格）缓存成一张离屏图，每帧只画扫描线 + 图标，预计能砍掉一半绘制成本。

3. `anonymous`（18.7%）：List 行 builder。可考虑把高频变化字段（RSSI、时间）拆成独立小节组件，减少整行重建范围。

## 9. P6 雷达每帧绘制降载（Energy2 复测后的第一优先项）

### 依据

Energy2 复测里 `drawRadar` 已经是最大的单项：**4,870 采样 = 20.2% 的已归因 JS CPU**（约 2.4s CPU / 49.7s ≈ 10% 单核）。改造前每帧要做：清屏 + 整屏填色 + 8 个圈层 + 十字线 + 4 段距离文字 + 16 段拖尾 + 扫描线 + 圆点分桶。

### 改动（`entry/src/main/ets/pages/fieldwatch/FieldwatchPage.ets`）

| # | 改动 | 说明 |
|---|---|---|
| 1 | **静态底板离屏缓存** | 底色 + 8 个圈层 + 十字 + 距离刻度是常量，现在烤进 `OffscreenCanvas` 的 `ImageBitmap`，稳态每帧只 `drawImage` 一次。指纹 = 绘制矩形 + 圆心 + 半径 + 四个配色值，任一变化才重画。 |
| 2 | **手势期不重建底板** | 平移/缩放期间圆心与半径每帧都在变，缓存必然失效；这时直接绘制，避免「多画一遍离屏」反而更慢。 |
| 3 | **失败自动降级** | 离屏画布创建失败时置 `backdropDisabled`，永久回退逐帧绘制并记 warn，不会每帧抛异常。 |
| 4 | **拖尾状态提到循环外** | 16 段拖尾同色同线宽，原来每段重设 `strokeStyle`/`lineWidth`，现在只在循环外设一次，循环里仅改 `globalAlpha`。 |
| 5 | **圈层比例数组提到模块级** | 原来每帧新建 `[0.125, ...]` 字面量并 `forEach` 闭包。 |
| 6 | **圆点从「每帧分桶」改为「点集变化时分桶」** | 原来每帧对每个点做 `dotKeys.indexOf('|' + key + '|')`（每点一次字符串拼接 + 线性检索）再建 `Map`。现在在 `replanRadarLabels()` 里一次性派生 `dotKeySet`（Set）与 `dotBuckets`（键 = 配色档+无线电类型）。 |
| 7 | **图标层同样改用 Set** | `buildRadarIcons` 的过滤条件原来是同款字符串检索，改成 `dotKeySet.has(key)`。 |

### 关键约束

- `@State dotKeys` **保留**（它驱动图标层重渲染），只把「判定」从字符串检索换成 Set；私有索引在 `replanRadarLabels()` 里**先于** `@State` 赋值写入，保证触发的 build 读到的是最新 Set。

## 12. P8 BLE / Wi-Fi 解析链优化（已完成，待人工验收）

### 依据（Energy3 采样）

| 函数 | 位置 | 采样 |
|---|---|---|
| `bytesHex` | BleScanner | 699 |
| `toObservation` | BleScanner | 737 |
| `hexOfBytes` | Parsers | 570 |
| `bytesOfHex` | Parsers | 389 |
| `decode` | Parsers | 217 |
| `refreshState` | ObservationCoordinator | 204 |
| `applyAd` | Parsers | 102 |
| 合计 | | **4,299（占全部采样 5.0%，≈2.15s / 52s）** |

### 三处根因与改法

#### 1. 逐字节拼十六进制（`bytesHex` / `hexOfBytes`）

原实现：

```ts
const value: string = data[index].toString(16).toUpperCase();
result += value.length === 1 ? '0' + value : value;
```

每字节 2~3 次临时字符串分配，字符串拼接本身还是 O(n²) 拷贝。改成 256 项查表 + `join('')`：
新增 `fieldwatch/domain/FieldwatchHex.ets`（`bytesToHex` / `bytesRangeToHex` / `hexToBytes` / `byteToHex`），三处实现（BLE / Wi-Fi / Parsers）收敛到同一份。

#### 2. 字节 → 十六进制 → 正则 → 再转回字节（`decodeBytes`）

原实现 `decodeBytes(raw)` 实际是 `decode(hexOfBytes(raw))`，于是每条广播都要：
字节转十六进制串 → 去掉冒号 → 正则校验 → 再解析回字节。真正的解析只需要字节。

改成：`decodeBytes` 直接进 AD 循环（`decodeFromBytes`），十六进制入口 `decode(hex)` 保留给单元测试与外部调用，行为不变。

另外 AD 字段取值原来写 `hexOfBytes(payload.slice(a, b))` —— 先分配子数组再逐字节拼串。改成 `bytesRangeToHex(payload, a, b)`，只剩最终字符串一次分配。

#### 3. 每条广播发布一次状态（`publishState`）

`onDeviceFind` 的循环里每条广播都调用 `publishState()`：一批最多 500 条 → 最多 500 次快照分配 + 500 次 coordinator 状态汇总 + 500 次应用状态写入。
而界面上「最近一次成功」只精确到秒。改成 **500ms 节流**（`publishStateThrottled`），`start()` 里重置时间戳保证首条广播立即发布。

#### 附带清理

- `toObservation` 里 `new Uint8Array(result.data)` 建了两次、整包十六进制转了两次 → 现在只取一次 `rawBytes`，解析与 `rawAdHex` 共用。
- 删除 `FieldwatchBleScanner` 里从未被调用的 `toHex(ArrayBuffer)`。

### 验证

- `assembleHap`：**BUILD SUCCESSFUL**（25s / 20s 两次）。
- 转换原语做了离线等价性校验：随机字节长度 0~300、区间切片、12 组畸形十六进制输入，共 **1,516 次比对，0 处不一致**。
- 未安装、未跑 hypium，真机回归由用户执行。

### 预期

- 每条广播的字节转换分配次数下降一个量级，整包 hex 往返被消除；
- 每秒数百条广播不再触发数百次状态发布；
- 对应 Energy3 的 5.0% 采样应有可观下降（下一次录制验证）。

## 13. P9 隐藏标签页的周期性重建治理（已完成，待人工验收）

### 依据

Energy3 里 `anonymous` 叶子合计 **2,594 采样（占全部 3.0%）**，其外层命名帧是 `rerender`（422）与 `drawRadar`（206）—— 说明时间花在**页面重建**上，而不是某个具体算法。

追下来根因不在实时页（它早就有 `visible` 闸门），而在另外两页：

| 页面 | 定时器 | 不可见时仍在做的事 |
|---|---|---|
| `FieldwatchSettingsPage` | 1000ms | 写 ~10 个 `@State` 字段 + 3 次 `checkPermission` 系统调用 + 一次通知状态查询 |
| `FieldwatchToolboxPage` | 2000ms | `tick += 1`（值必变 → **强制整页重建**）+ `setTimeout(drawChart)` 重画画布 |

`Tabs` 会让所有 `TabContent` 常驻，`aboutToAppear` 里的定时器不会因为「切到别的标签」而停 —— 用户在实时页滑雷达时，设置页和工具箱页仍在每秒/每两秒各自重建一次。

### 改法

1. **两页都加 `@Prop @Watch('onPageVisibleChanged') pageVisible: boolean = true;`**，定时回调里 `if (!this.pageVisible || !isAppForeground()) return;`。
   沿用 `FieldwatchSignaturesPage` 已经验证过的 `pageVisible` 命名（该组件有同名 `visible()` 方法，叫 `visible` 会撞名）。
2. **`@Watch` 在切到本页时立刻 `refresh()` 一次**，避免「切过去要等一个定时周期才更新」的迟滞。
3. **权限快照加 500ms 缓存**（`FieldwatchApplication.permissionSnapshot()`）：
   原来 Live 页 / 设置页 / 根页各每秒问一次，同一秒最多 3 个调用方 × 3 条权限 = 9 次 accessToken 系统调用。
   缓存后 ≤6 次/秒；`requestPermission()` 成功时把时间戳清零，保证刚授予的权限下一帧就可见。
   注意**每次返回新对象** —— 调用方会把快照挂到自己的 `@State` 上，共用实例会让「引用相同」导致界面不刷新。

## 14. P10 雷达绘制层收拢（已完成，待人工验收）

### 依据

`drawRadar` 在 Energy3 里仍占 **1,579 采样（1.8%）**。逐帧路径（62.5fps）当时是：

1. `drawImage` 贴静态底板（已缓存，便宜）；
2. 16 段拖尾 + 1 条扫描线（17 次 `beginPath`/`stroke`）；
3. **逐帧重建全部圆点路径**：按配色分桶后 `beginPath` + `arc × N` + `fill`。

第 3 步与扫描角无关 —— 圆点只在数据或几何变化时才动，却在每一帧重画。

### 改法

- 抽出 `paintRadarDots()`，由 `paintRadarBackdrop()` 末尾调用，**圆点随底板一起烤进离屏位图**；
  `drawRadar` 里逐帧的圆点循环删除。
- `rebuildDotIndex()` 顺带算出 `dotToken`（点集大小 + 归一化坐标的滚动哈希），并入底板指纹，
  精度取 1/100：更细的变化画面看不出来，却会让缓存每秒失效。
- 圆弧层的 `span` 改用**真实（可能带小数）画布尺寸**：位图按 `ceil()` 建，
  用整数尺寸算 `min(w,h)` 会与 ArkUI 图标层差最多 1px（表现为圆点相对圆环偏移）。

稳态每帧只剩：`drawImage` + 16 段拖尾 + 1 条扫描线。
手势期间仍走直绘路径（`interacting` → 指纹为空），行为与改造前一致。

### 验证

- `assembleHap`：**BUILD SUCCESSFUL**（23s）。未安装，真机验收由用户执行。

## 16. i18n 覆盖治理（本次完成）

### 问题形态

英文模式下大量界面仍是中文。拆开看是两类问题，之前只处理了表面：

| 类型 | 表现 | 规模 |
|---|---|---|
| **硬编码中文字面量** | 文案直接写在 `.ets` 里，根本没进资源表 | 355 处 |
| **en_US 资源值仍是中文** | 资源存在但没翻译 | 37 条 |
| **切语言后部分文本不刷新** | `@Builder` 字符串参数在首次构建时固化 | 见下 |

### 1. 资源文本缓存下沉到框架层

`ngf_framework/i18n/utils/ResourceTextCache.ets` 新增 `ngfText(key)` / `invalidateNGFTextCache()`；

**为什么下沉**：领域层（`fieldwatch/domain/**`：设备解释、候选特征、小组件文案）也要取本地化文本，

### 3. en_US 资源补齐（37 条）

  且 base 里这 13 条的值被破坏成 `just_now', ['たった今` 这种拼接残骸 —— 一并修正为中/英。
- 结果：`en_US` 中文残留 **0 条**，与 base 键集完全一致（各 2663 条）。

### 4. 切语言后整棵树重建

`applyAppLanguage()` 在写完覆盖值后调用 `windowStage.loadContent(...)` 重建页面树。

**为什么必须这样**：一部分文案是通过 `@Builder` 的字符串参数往下传的
（`this.section(title, hint)`、`this.buildToolTab(label, index)` 等），这类文本在首次构建时固化，
语言切换只做状态刷新覆盖不到 —— 实测表现就是「切了英文，一半页面还是中文」这种中英混杂。
重建页面树让所有 `fieldwatchText()` 重新解析，代价是回到实时页、路径栈清空（低频操作可接受）。

为此在 `PlatformWindowManagerFacade` 新增了 `getWindowStage()`。
